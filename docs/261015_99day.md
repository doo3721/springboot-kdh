# **JPQL(Java Persistence Query Language)과 객체지향 쿼리**

## **1. JPQL 정의 및 표준 SQL과의 차이점**

- JPQL(Java Persistence Query Language)은 데이터베이스 테이블이 아닌 JPA 엔티티 객체를 대상으로 질의를 수행하는 객체지향 쿼리 언어.
- 특정 데이터베이스 벤더(MySQL, PostgreSQL, Oracle 등)의 SQL 문법에 종속되지 않고, 설정된 방언(Dialect)을 기반으로 실행 시점에 해당 데이터베이스 전용 SQL로 자동 번역됨.
- 객체지향 모델링을 온전히 유지하면서 복잡한 검색 쿼리를 처리할 수 있으며, 연관 엔티티의 객체 그래프 탐색 문법을 지원함.

### **1.1 JPQL과 표준 SQL의 핵심 차이점**

- 질의 대상
    - SQL: 데이터베이스의 테이블명과 물리 컬럼명을 직접 대상으로 쿼리를 작성함.
    - JPQL: 자바 소스코드에 매핑된 엔티티 클래스명과 엔티티 필드(프로퍼티)명을 대상으로 쿼리를 작성함.
- 대소문자 구분 규칙: `SELECT`, `FROM`, `WHERE` 등 JPQL 예약어는 대소문자를 가리지 않으나, 엔티티 클래스명(`Post`)과 프로퍼티명(`likeCount`, `member`)은 자바 코드와 동일하게 대소문자를 엄격하게 구분함.
- 엔티티 별칭(Alias) 필수 선언: JPQL의 `FROM` 절에서는 대상 엔티티에 대한 별칭(예: `FROM Post p`)을 필수로 선언해야 하며, 프로퍼티 참조 시 해당 별칭을 통해 접근함 (`AS` 키워드는 생략 가능).

## **2. JPQL 기본 문법 구조와 객체 그래프 탐색**

JPQL은 표준 SQL과 유사한 절(Clause) 구조를 제공하며 엔티티 객체 단위로 데이터를 조회함.

### **2.1 기본 쿼리 절 구조**

- SELECT 절: 조회할 엔티티 또는 특정 속성을 지정함 (`SELECT p FROM Post p`).
- FROM 절: 조회 대상 엔티티 클래스명을 지정하며 별칭 선언이 필수 (`Post p`).
- WHERE 절: 필터링 조건을 지정하며 엔티티 필드명을 대상으로 비교 연산을 수행함 (`WHERE p.likeCount >= 10`).
- ORDER BY 절: 정렬 기준 필드를 지정함 (`ORDER BY p.id DESC`).

### **2.2 객체 그래프 탐색 기본 원리**

- 점(`.`) 표기법을 사용하여 엔티티가 참조하고 있는 연관 객체의 필드에 직접 접근하는 방식.
- 단일 값 연관 경로 탐색: 게시글(`Post`) 엔티티를 조회하면서 연관된 작성자(`Member`)의 닉네임을 조건절에서 참조 가능 (`WHERE p.member.nickname = '하루'`).
- 기본 JPQL 작성 예시

    ```sql
    -- 작성자 닉네임이 '하루'이고 좋아요 수가 10 이상인 게시글을 ID 내림차순으로 정렬 조회
    SELECT p FROM Post p WHERE p.member.nickname = '하루' AND p.likeCount >= 10 ORDER BY p.id DESC
    ```

- 데이터베이스에서 실제 실행되는 변환 SQL

    ```sql
    -- p.member.nickname 탐색으로 인해 member 테이블과의 내부 조인(INNER JOIN)이 자동 생성됨
    SELECT
        p.id,
        p.content,
        p.image_url,
        p.like_count,
        p.member_id,
        p.created_at,
        p.updated_at
    FROM
        post p
    INNER JOIN
        member m ON p.member_id = m.id
    WHERE
        m.nickname = '하루'
        AND p.like_count >= 10
    ORDER BY
        p.id DESC
    ```


# **Spring Data JPA 쿼리 메서드와 페이징**

## **1. 메서드 이름 기반 쿼리 생성**

리포지토리 인터페이스에 정해진 명명 규칙에 맞추어 메서드 이름을 선언하면, Spring Data JPA가 애플리케이션 기동 시점에 이름을 분석하여 적절한 JPQL을 자동으로 조립하고 데이터베이스 쿼리를 실행함.

### **1.1 쿼리 메서드 구조 및 파싱 메커니즘**

메서드 이름은 주어부와 술어부(조건절)가 `By` 키워드를 기점으로 결합되는 규칙을 준수함.

- 주어부
    - `find...By`, `read...By`, `get...By`, `query...By`, `search...By`: 기본 엔티티 조회 쿼리 구성.
    - `count...By`: 조건에 부합하는 레코드 건수 반환 (`Long`).
    - `exists...By`: 조건에 부합하는 데이터 존재 여부 반환 (`boolean`).
    - `delete...By`, `remove...By`: 조건에 부합하는 데이터 삭제 쿼리 실행 (`Long` 또는 `void`).
    - 주어부 수식어 및 도메인 명사 활용
        - `Distinct`, `First<N>`, `Top<N>`을 추가하여 중복 제거 및 조회 결과 건수를 제한할 수 있음.
        - `findPostsBy...`, `findAllBy...`처럼 `By` 앞에 도메인 명사나 서술어를 덧붙여도 Spring Data JPA는 이를 단순 플레이스홀더로 인식하여 정상 처리함.
- 술어부 (조건절)
    - `By` 키워드 뒤에 선언되며 엔티티의 프로퍼티명과 연산자 키워드를 조합하여 `WHERE` 조건절을 생성함.
    - 연산자 키워드를 생략하면 동등 비교(`=`) 조건이 기본으로 적용됨.

### **1.2 지원 키워드 및 생성 쿼리 매핑**

| **키워드 범주** | **메서드 이름 샘플** | **생성되는 JPQL 조건절 구문** |
| --- | --- | --- |
| 포함 검색 | findByContentContaining(String keyword) | where p.content like %:keyword% |
| 대소 비교 | findByLikeCountGreaterThanEqual(int count) | where p.likeCount >= :count |
| 다중 조건 | findByContentContainingAndLikeCountGreaterThanEqual(String keyword, int count) | where p.content like %:keyword% and p.likeCount >= :count |
| 범위 검색 | findByCreatedAtBetween(LocalDateTime startDateTime, LocalDateTime endDateTime) | where p.createdAt between :startDateTime and :endDateTime |
| 목록 포함 | findByMemberIn(Collection members) | where p.member in (:members) |
| 정렬 | findByMemberIdOrderByCreatedAtDesc(Long memberId) | where p.member.id = :memberId order by p.createdAt desc |
| 개수 제한 | findFirst3ByOrderByLikeCountDesc() | order by p.likeCount desc limit 3 |
| 존재 여부 | existsByEmail(String email) | select case when count(m)>0 then true else false |
| 건수 집계 | countByMemberId(Long memberId) | select count(p) where p.member.id = :memberId |

#### **1) PostRepository 인터페이스**

- src/main/java/net/likelion/bebc25/jpasns/repository/PostRepository.java

    ```java
    public interface PostRepository extends JpaRepository<Post, Long> {
    
        // 특정 회원 작성한 게시글 목록을 조회(최신 등록 순으로)
        List<Post> findByMemberOrderByCreatedAtDesc(Member member);
    
        // 전체 게시글 목록을 최신 등록순으로 정렬 조회
        List<Post> findByOrderByCreatedAtDesc();
    
        // 회원 식별자(PK)를 조건으로 게시글 목록 최신순 조회
        List<Post> findByMember_IdOrderByCreatedAtDesc(Long memberId);
    
        // 전체 게시글 목록을 키워드 포함 최신 등록순으로 정렬 조회
        List<Post> findByContentContainingOrderByCreatedAtDesc(String keyword);
    
        // 회원 식별자(PK)를 조건으로 본문에 키워드 포함 검색 최신 등록순으로 정렬 조회
        List<Post> findByMember_IdAndContentContainingOrderByCreatedAtDesc(Long memberId, String keyword);
    
        // 본문 키워드 포함 검색
        List<Post> findByContentContaining(String keyword);
    
        // 특정 좋아요 수 이상의 인기 게시글 조회
        List<Post> findByLikeCountGreaterThanEqual(int minLikeCount);
    
        // 특정 회원의 특정 좋아요 수 이상 게시글 최신순 정렬 조회 (조건 누적으로 메서드명이 길어진 쿼리 메서드)
        List<Post> findByMember_IdAndLikeCountGreaterThanEqualOrderByCreatedAtDesc(
            Long memberId,
            int minLikeCount
        );
    }
    ```


#### **2) 테스트 케이스 작성**

- src/test/java/net/likelion/bebc25/jpasns/repository/PostRepositoryTest.java

    ```java
    package net.likelion.bebc25.jpasns.repository;
    
    import net.likelion.bebc25.jpasns.domain.Post;
    import org.junit.jupiter.api.DisplayName;
    import org.junit.jupiter.api.Test;
    import org.springframework.beans.factory.annotation.Autowired;
    import org.springframework.boot.test.context.SpringBootTest;
    import org.springframework.transaction.annotation.Transactional;
    
    import java.util.List;
    
    import static org.assertj.core.api.Assertions.assertThat;
    
    @SpringBootTest
    @Transactional
    class PostRepositoryTest {
    
        @Autowired
        private PostRepository postRepository;
    
        @Test
        @DisplayName("본문 키워드 포함 조건 검색")
        void findByContentContaining() {
            // Given: 검색 키워드 지정
            String keyword = "스프링 부트";
    
            // When: 본문 LIKE %키워드% 조회
            List<Post> posts = postRepository.findByContentContaining(keyword);
    
            // Then: 반환된 모든 게시글 본문에 키워드 포함 여부 확인
            assertThat(posts).isNotEmpty();
            assertThat(posts).allMatch(post -> post.getContent().contains(keyword));
        }
    
        @Test
        @DisplayName("특정 좋아요 수 이상인 인기 게시글 목록 필터링 조회")
        void findByLikeCountGreaterThanEqual() {
            // Given: 최소 좋아요 기준 수치
            int minLikeCount = 3;
    
            // When: 대소 비교(>=) 조건 조회
            List<Post> posts = postRepository.findByLikeCountGreaterThanEqual(minLikeCount);
    
            // Then: 조건 수치 이상 여부 검증
            assertThat(posts).isNotEmpty();
            assertThat(posts).allMatch(post -> post.getLikeCount() >= minLikeCount);
        }
    
        @Test
        @DisplayName("특정 회원의 좋아요 수 조건 이상 게시글 최신순 정렬 조회")
        void findByMember_IdAndLikeCountGreaterThanEqualOrderByCreatedAtDesc() {
            // Given: 회원 식별자 및 최소 좋아요 조건
            Long memberId = 2L;
            int minLikeCount = 3;
    
            // When: 다중 조건 및 정렬 결합 쿼리 메서드 호출
            List<Post> posts = postRepository.findByMember_IdAndLikeCountGreaterThanEqualOrderByCreatedAtDesc(
                memberId,
                minLikeCount
            );
    
            // Then: 다중 조건 충족 및 등록일시 내림차순 정렬 상태 검증
            assertThat(posts).isNotEmpty();
            assertThat(posts).allMatch(post -> post.getMember().getId().equals(memberId) && post.getLikeCount() >= minLikeCount);
            assertThat(posts).isSortedAccordingTo((p1, p2) -> p2.getCreatedAt().compareTo(p1.getCreatedAt()));
        }
    }
    ```

- 테스트 검증 핵심 포인트
    - 본문 키워드 검색: `Containing` 키워드를 통해 SQL의 `LIKE %keyword%` 조건이 바인딩되어 대상 키워드를 포함한 게시글만 반환되는지 확인.
    - 대소 비교 필터링: `GreaterThanEqual` 키워드를 통해 지정한 기준 수치 이상의 좋아요를 보유한 레코드만 필터링되는지 확인.
    - 다중 조건 및 정렬 결합: `And` 키워드로 회원 식별자와 좋아요 수 조건을 동시 만족하고, `OrderByCreatedAtDesc`에 의해 최신 등록순으로 정렬되는지 확인.
    - 정렬 순서 단언(`isSortedAccordingTo`): AssertJ의 정렬 검증 메서드로, `Comparator` 람다식을 전달하여 리스트의 요소들이 지정한 순서 규칙대로 정렬되어 있는지 확인함. (람다식의 결과가 모두 음수이거아 0이면 테스트 통과)
    - `compareTo` 메서드의 역할 및 내림차순 판정 원리
        - 두 객체의 순서를 비교하여 음수(작음), 0(같음), 양수(큼)를 반환하는 `Comparable<T>` 인터페이스의 표준 규약.
        - `LocalDateTime` 비교 시 과거 시점은 미래 시점보다 작은 값으로 처리됨 (`과거.compareTo(미래)`는 음수 반환).
        - `Comparator` 규약은 `(p1, p2)` 비교 연산의 결과가 음수일 때 앞의 원소(`p1`)가 우선순위를 갖고 앞자리를 유지하도록 판단함.
        - 따라서 내림차순(최신순) 정렬 검증 시 `p2.getCreatedAt().compareTo(p1.getCreatedAt())` 형태로 비교 대상을 뒤바꾸어 호출함. 선행 글(`p1`)이 최신(미래)이고 후행 글(`p2`)이 과거일 때 `과거(p2).compareTo(미래(p1))`의 결과가 음수가 되므로, 최신 글이 앞에 배치된 정상 상태로 판정함.

### **1.3 스프링 컨테이너 구동 시점의 정적 검증 메커니즘**

- Spring Data JPA는 스프링 애플리케이션이 초기화되는 컨텍스트 로딩 시점에 등록된 모든 리포지토리 인터페이스의 메서드명을 전수 검사함.
- 메서드명에 명시된 프로퍼티가 대상 엔티티에 존재하지 않거나 오타가 발생하면 `PropertyReferenceException`을 발생시켜 애플리케이션 구동을 즉시 실패시킴.
- 런타임에 실제 사용자 요청이 인입된 후 쿼리 문법 에러가 발생하는 사고를 방지하고, 초기 구동 단계에서 조기에 휴먼 에러를 탐지하는 안전장치 역할을 수행함.

### **1.4 쿼리 메서드의 구조적 한계와 대안 전환 기준**

- 조건 절이 3개 이상 늘어나면 메서드명이 지나치게 길어져 코드 가독성과 유지보수성이 급격히 저하됨.
- 연관 엔티티의 복합 조인, 페치 조인 제어, 서브쿼리, 통계 집계 등 복잡한 비즈니스 쿼리를 표현하기 어려움.
- 실무 쿼리 기술 전환 기준
    - 단순 단일 및 2중 조건 조회: 메서드 이름 기반 쿼리 메서드 적용.
    - 다중 조인, 페치 조인, 특정 DTO 직접 매핑, 통계성 정적 쿼리: `@Query`(JPQL) 적용.
    - 다중 검색 필터, 동적 정렬, 가변 조건 기반 동적 쿼리: QueryDSL 적용.

## **2. @Query를 활용한 리포지토리 JPQL 선언**

메서드 이름 기반 쿼리가 지나치게 길어지거나 복잡한 연관관계 조인, 파라미터 바인딩, DTO 직접 프로젝션이 필요할 때는 `@Query` 어노테이션을 사용하여 리포지토리 메서드에 JPQL을 직접 선언해서 사용.

### **2.1 파라미터 바인딩 메커니즘**

- 위치 기반 바인딩(`?1`, `?2`): 파라미터 선언 순서가 바뀌면 쿼리 실행 오류나 잘못된 데이터 매핑 사고를 유발하므로 실무 사용을 지양함.
- 이름 기반 바인딩(`:paramName`): `@Param` 어노테이션과 파라미터 이름을 일치시켜 순서와 무관하게 안전하게 매핑되도록 선언하는 실무 표준 방식.

### **2.2 JPQL 조인 문법과 묵시적 조인의 위험성**

- 명시적 조인(Explicit Join)
    - 내부 조인(INNER JOIN): `SELECT p FROM Post p JOIN p.member m` (연관 데이터가 양쪽에 모두 존재하는 경우만 조회하며 `INNER` 키워드는 생략 가능).
    - 외부 조인(LEFT OUTER JOIN): `SELECT p FROM Post p LEFT JOIN p.member m` (연관된 회원이 없더라도 게시글 기준 데이터를 누락 없이 조회).
- 묵시적 조인(Implicit Join)의 위험성과 원칙
    - 점(`.`) 표기법을 통해 연관 엔티티의 필드에 직접 접근할 때 JPA가 배후에서 SQL 내부 조인을 자동 조립하는 현상 (`SELECT p.member.nickname FROM Post p`).
    - 항상 내부 조인(`INNER JOIN`)으로 번역되므로 연관 데이터가 없는 경우 기준 데이터까지 누락되는 버그를 유발하며, 쿼리 실행 계획을 예측하기 어려움.
    - 실무 원칙: 묵시적 조인은 지양하고, 조인이 필요한 경우에는 항상 `JOIN` 키워드를 명시적으로 선언하여 실행 계획과 쿼리 가독성을 통제함.

### **2.3 DTO 프로젝션과 new 문법**

- 엔티티를 영속성 컨텍스트에 로딩(1차 캐시 등록)하지 않고, 화면이나 API 응답에 필요한 특정 컬럼만 데이터베이스에서 직접 조회하여 순수 DTO 객체로 즉시 매핑할 때 JPQL의 `new` 문법을 활용함.
- 영속성 관리 배제에 따른 최적화 효과
    - 영속성 컨텍스트(1차 캐시)를 완전히 우회(Bypass)하므로 1차 캐시 엔티티 보관, 스냅샷 생성, 변경 감지(더티 체킹) 연산 오버헤드가 전혀 발생하지 않음.
    - DTO 내부 필드를 수정하더라도 데이터베이스 UPDATE가 발생하지 않는 순수 읽기 전용 데이터로 동작함.
    - 대량 목록 및 통계성 단순 조회 시 힙 메모리 점유율과 가비지 컬렉션(GC) 부하를 대폭 절감함.
- 조회 전용 DTO 분리 원칙과 기존 엔티티 재사용 지양 사유
    - 기존 엔티티에 특정 필드만 받는 생성자를 선언하여 `new Post(...)` 형태로 프로젝션하는 방식은 심각한 부작용을 유발하므로 별도의 조회 전용 DTO(Record)를 설계해야 함.
    - 불완전한 객체로 인한 런타임 오류 방지: 명시한 컬럼만 채워지고 나머지 필드가 null로 비어 있는 불완전한 엔티티가 생성되어, 후속 비즈니스 로직이나 객체 그래프 탐색 시 `NullPointerException`이 발생할 위험이 있음.
    - 데이터 덮어쓰기 오염 방지: 비영속 상태의 불완전한 엔티티 객체를 영속 상태로 오인하여 `save()`나 변경 처리를 시도할 경우, 비어 있던 null 값들이 데이터베이스로 반영되어 기존 데이터가 영구적으로 유실되는 사고를 초래함.
    - 도메인 캡슐화 및 무결성 유지: 화면 요구사항에 맞춘 무분별한 생성자 추가로 도메인 엔티티의 책임이 오염되는 것을 차단하고, 도메인 규칙과 화면 표현 영역을 엄격히 분리함.
- JPQL `SELECT` 절에 DTO 클래스의 전체 패키지 경로를 명시해야 하며, 조회 컬럼 순서 및 타입과 일치하는 생성자가 준비되어 있어야 함.

## **3. Pageable과 페이징 및 정렬 처리**

대용량 데이터 환경에서 전체 레코드를 메모리에 한 번에 적재하면 메모리 부족(OOM)과 심각한 쿼리 지연이 발생함. Spring Data JPA는 데이터베이스의 `LIMIT`, `OFFSET` 절을 추상화한 `Pageable` 인터페이스와 정렬(`Sort`), 다양한 반환 타입(`Page`, `Slice`, `List`)을 제공하여 체계적인 페이징 조회를 지원함.

### **3.1 Pageable 인터페이스와 PageRequest 생성**

- `Pageable` 인터페이스: 페이지 번호, 페이지 크기, 정렬 조건을 캡슐화한 인터페이스.
- `PageRequest` 구현체: `Pageable`의 표준 구현체로, 정적 팩토리 메서드 `PageRequest.of()`를 통해 생성함.
    - 기본 페이징: `PageRequest.of(page, size)`
    - 정렬 결합 페이징: `PageRequest.of(page, size, Sort.by(Sort.Direction.DESC, "createdAt"))`
- 0-based 페이지 인덱스: Spring Data JPA의 페이지 번호는 0부터 시작함. 클라이언트가 1페이지를 요구할 경우 서비스 계층에서 `page - 1` 처리를 수행하거나 파라미터 매핑 정책을 일관되게 수립해야 함.
    - `PageRequest.of(0, 10)`: 1페이지, 페이지당 10개 조회 (SQL: `LIMIT 10 OFFSET 0`).
    - `PageRequest.of(1, 10)`: 2페이지, 페이지당 10개 조회 (SQL: `LIMIT 10 OFFSET 10`).

### **3.2 페이징 반환 타입별 동작 원리와 성능 비교**

#### **1) Page의 동작 원리**

- 본문 데이터 조회 쿼리와 함께 전체 레코드 수를 계산하는 `SELECT COUNT(*)` 쿼리를 추가 실행함.
- 전체 데이터 건수를 바탕으로 총 페이지 수와 마지막 페이지 여부를 정확하게 연산함.
- 주요 활용처: 번호 네비게이션 버튼(1, 2, 3... [다음])이 필요한 전통적인 웹 게시판.
- 주요 편의 메서드
    - `getContent()`: 조회된 현재 페이지의 엔티티 목록 반환 (`List<T>`).
    - `getTotalElements()`: 조건에 부합하는 전체 데이터 총 건수.
    - `getTotalPages()`: 전체 페이지 수 (`(totalElements + size - 1) / size`).
    - `getNumber()`: 현재 페이지 번호 (0부터 시작).
    - `getSize()`: 한 페이지당 조회 크기.
    - `hasNext()` / `hasPrevious()`: 다음 페이지 및 이전 페이지 존재 여부.
    - `isFirst()` / `isLast()`: 첫 번째 페이지 및 마지막 페이지 여부.

#### **2) Slice의 동작 원리와 limit + 1 메커니즘**

- 전체 카운트 쿼리를 실행하지 않고, 요청한 크기(`size`)보다 1개 더 많은 레코드를 조회(`LIMIT size + 1`)함.
- 추가 1건의 데이터가 실제로 조회되는지 여부만으로 `hasNext()`를 판별함.
- 조회된 결과 리스트에서 마지막 1건을 자동으로 제거한 뒤 `size`만큼의 본문 데이터만 클라이언트에 전달함.
- 주요 활용처: 전체 건수가 불필요한 모바일 앱의 '더보기' 버튼이나 무한 스크롤(Infinite Scroll) 피드 UI.
- 성능상 이점: 수백만 건 이상의 대용량 테이블에서 카운트 쿼리 실행 부하를 원천 배제하여 빠른 응답 속도를 확보함.

### **3.3 계층별 페이징 구현**

#### **1) 리포지토리 계층 페이징 메서드 확장 (src/main/java/net/likelion/bebc25/jpasns/repository/PostRepository.java)**

- Spring Data JPA가 `Pageable`을 감지하여 방언에 맞는 `LIMIT` 및 `OFFSET` 페이징 SQL을 자동 조립하고, 전체 레코드 수를 집계하는 `COUNT` 쿼리를 함께 실행함.
- 조건 없는 전체 목록 페이징의 경우 `JpaRepository` 기본 제공 메서드인 `findAll(Pageable pageable)`을 그대로 호출함.
- 페이징 확장 리포지토리 메서드 선언

    ```
    // 1. 특정 회원 식별자 및 본문 키워드 조건 페이징 (기존 @Query JPQL 확장)
    @Query("SELECT p FROM Post p JOIN p.member m WHERE m.id = :memberId AND p.content LIKE %:keyword% ORDER BY p.createdAt DESC")
    Page<Post> findByMemberAndKeyword(
        @Param("memberId") Long memberId,
        @Param("keyword") String keyword,
        Pageable pageable
    );
    
    // 2. 특정 회원 식별자 조건 최신순 페이징 (기존 쿼리 메서드 확장)
    Page<Post> findByMember_IdOrderByCreatedAtDesc(Long memberId, Pageable pageable);
    
    // 3. 본문 키워드 포함 조건 최신순 페이징 (기존 쿼리 메서드 확장)
    Page<Post> findByContentContainingOrderByCreatedAtDesc(String keyword, Pageable pageable);
    ```


#### **2) 서비스 계층 구현 (src/main/java/net/likelion/bebc25/jpasns/service/PostService.java)**

- 리포지토리 페이징 메서드 호출 시 `pageable`을 전달하고, 최종 반환된 `Page<Post>`를 `page.map(PostDto.Response::from)`으로 DTO 변환하여 반환함.

    ```java
    // 1. 순수 전체 목록 페이징 (별도 조건 없이 JpaRepository 기본 findAll 활용)
    public Page<PostDto.Response> getPosts(Pageable pageable) {
        Page<Post> posts = postRepository.findAll(pageable);
        return posts.map(PostDto.Response::from);
    }
    
    // 2. 검색 조건(회원 식별자, 검색 키워드) 결합 다중 분기 페이징
    public Page<PostDto.Response> getPosts(Long memberId, String keyword, Pageable pageable) {
        boolean hasKeyword = keyword != null && !keyword.isBlank();
        Page<Post> posts;
    
        if (memberId != null) {
            if (!memberRepository.existsById(memberId)) {
                throw new IllegalArgumentException("존재하지 않는 회원입니다. id=" + memberId);
            }
    
            if (hasKeyword) {
                posts = postRepository.findByMemberAndKeyword(memberId, keyword, pageable);
            } else {
                posts = postRepository.findByMember_IdOrderByCreatedAtDesc(memberId, pageable);
            }
        } else {
            if (hasKeyword) {
                posts = postRepository.findByContentContainingOrderByCreatedAtDesc(keyword, pageable);
            } else {
                posts = postRepository.findAll(pageable);
            }
        }
    
        return posts.map(PostDto.Response::from);
    }
    ```


#### **3) 컨트롤러 계층 연동 (src/main/java/net/likelion/bebc25/jpasns/controller/PostController.java)**

- 기존의 `memberId`, `keyword` 검색 파라미터와 함께 `@PageableDefault`가 적용된 `Pageable` 객체를 주입받음.
- 클라이언트의 조건 검색 및 페이징 요청(`GET /api/v1/posts?memberId=1&keyword=스프링&page=0&size=10`)을 일괄 수용하여 서비스로 위임함.

    ```java
    @GetMapping
    public ResponseEntity<Page<PostDto.Response>> getPosts(
        @RequestParam(required = false) Long memberId,
        @RequestParam(required = false) String keyword,
        @PageableDefault(page = 0, size = 10, sort = "createdAt", direction = Sort.Direction.DESC) Pageable pageable
    ) {
        Page<PostDto.Response> response = postService.getPosts(memberId, keyword, pageable);
        return ResponseEntity.ok(response);
    }
    ```

- 구조적 한계와 발전 과제: 검색 조건이 추가될 때마다 서비스의 if-else 분기와 리포지토리 메서드가 기하급수적으로 늘어나는 한계가 발생하며, 이는 다음 3단원의 QueryDSL 동적 쿼리를 통해 단일 쿼리로 통합 해결함.
