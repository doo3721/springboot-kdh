## 2교시: 사용자 정의 어노테이션, 리플렉션을 이용한 어노테이션 동적처리, 프록시 패턴과 AOP

- 사용자 정의 어노테이션 (Custom Annotation)
    - 선언 문법
        - @interface 키워드를 사용하여 새로운 어노테이션 정의를 선언
        - 메타 어노테이션(@Target, @Retention 등)을 선언부에 적절히 명시하여 어노테이션의 목적과 수명을 규정해야 함
    - 어노테이션 엘리먼트(속성) 선언:
        - 어노테이션 내부 필드는 메소드 형태로 선언, 기본값은 default 키워드로 지정 가능
        - 사용할 수 있는 타입은 기본 타입, String, Class, Enum, Annotation 및 이들의 배열로 제한
        - 속성 선언 예시

            ```java
            @Target(ElementType.METHOD)
            @Retention(RetentionPolicy.RUNTIME)
            public @interface RequestMapping {
              String value(); // 필수 속성 (값을 기입하지 않으면 컴파일 에러)
              String method() default "GET"; // 기본값이 지정된 선택 속성
            }
            ```

        - 속성 적용 예시

            ```java
            // 1. value 속성만 단독으로 지정하는 경우 (속성명 생략 가능)
            @RequestMapping("/list")
            public void getList() {
            }
            
            // 2. 여러 속성을 동시에 지정하는 경우 (속성명 명시 필요)
            @RequestMapping(value = "/save", method = "POST")
            public void savePost() {
            }
            ```

- 리플렉션을 활용한 어노테이션 동적 처리
    - 어노테이션의 기능 제한
        - 어노테이션은 컴파일러나 런타임에 힌트를 공급하는 정적인 메타데이터일 뿐, 어떠한 실행 코드도 포함하지 않음
        - 따라서 어노테이션의 지시사항대로 실제 로직을 실행해 주는 처리 주체(Processor)의 구현이 수반되어야 함
    - 리플렉션을 통한 감지 및 실행
        - java.lang.reflect 패키지의 API들을 활용하여 실행 시점(Runtime)에 대상 클래스의 어노테이션을 동적으로 조사하고 처리 로직을 구동함
        - 리플렉션 프로세서 예시

            ```java
            // 어노테이션을 감지하여 메서드 실행 시간을 측정해 주는 프로세서
            public class TimeProcessor {
              public void process(Object target) {
                Method[] methods = target.getClass().getDeclaredMethods();
                for (Method method : methods) {
                  // @MeasureTime 어노테이션이 부착된 메서드인지 감지
                  if (method.isAnnotationPresent(MeasureTime.class)) {
                    MeasureTime measureTime = method.getAnnotation(MeasureTime.class);
                    // value 속성값이 없으면 메서드명을, 있으면 설정된 작업명을 사용
                    String taskName = measureTime.value().isEmpty() ? method.getName() : measureTime.value();
            
                    long start = System.currentTimeMillis();
                    try {
                      method.invoke(target); // 메서드 동적 실행
                    } catch (Exception e) {
                      e.printStackTrace();
                    }
                    long end = System.currentTimeMillis();
                    System.out.println(taskName + " 소요 시간: " + (end - start) + "ms");
                  }
                }
              }
            }
            ```

- 프록시 패턴과 AOP를 통한 기능 자동화
    - 수동 프로세서 호출의 한계
        - 비즈니스 코드 실행 도중 매번 processor.process(service)와 같이 동적으로 분석기를 수동 호출하는 코드가 들어가면 결합도가 증가하고 가독성이 저하됨
    - 프록시(Proxy)를 통한 가로채기
        - 클라이언트가 원본 객체를 직접 가리키는 대신, 동일한 인터페이스를 구현한 가짜 대리인(Proxy)을 호출하도록 구조를 형성함
        - 프록시 객체가 호출을 중간에 가로채서 어노테이션 유무에 따라 시간 측정이나 트랜잭션 등의 부가 로직을 선처리하고, 실제 핵심 비즈니스 메소드를 최정적으로 대리 호출해 줌
    - 스프링 AOP의 기여
        - Spring 프레임워크는 개발자가 번거롭게 프록시 객체를 매번 직접 코딩할 필요없이, 어노테이션 설정만으로 프록시의 생성과 빈(Bean) 바인딩 과정을 완전 자동화하여 프레임워크 수준에서 대행해 줌
        - AOP

          [[Spring] 스프링 AOP (Spring AOP) 총정리 : 개념, 프록시 기반 AOP, @AOP](https://engkimbs.tistory.com/entry/%EC%8A%A4%ED%94%84%EB%A7%81AOP)


## 3~4교시: 단위/통합 테스트, JUnit 5 라이브러리

- 단위 테스트 (Unit Test)
    - 소스 코드의 특정 모듈(주로 개별 메소드)이 의도한 대로 정확히 작동하는지 독립적으로 검증하는 과정
    - 격리된 테스트 환경 구성을 통해 동작 여부를 신속하게 감별하고 버그를 조기에 발견할 수 있음
    - 이점
        - 코드 변경이나 대규모 리팩토링 진행 시 기존 기능의 파손 여부를 감지해 주는 안전장치 역할 수행
        - 수동으로 메인 메소드를 반복 실행하여 확인하는 디버깅 시간을 줄임
- 통합 테스트 (Integration Test)
    - 두 개 이상의 소프트웨어 모듈, 데이터베이스, 네트워크 등 여러 구성 요소 간 상호작용일 올바르게 이루어지는지 유기적으로 검증하는 과정
    - 개별 모듈들을 조립하여 연동했을 때 발생하는 데이터 매핑 오류, 설정 결함, 트랜잭션 예외 등의 연계 결함을 포착하는데 중점
    - 통합 테스트 진행 방식
        - 스프링 부트 환경에서는 실제 컨테이너를 구동하여 빈 객체를 연동하는 @SpringBootTest 기법을 주로 활용
        - 테스트용 데이터베이스(인메모리 DB인 H2 또는 가상 컨테이너 기술)를 직접 연동하여 쿼리 동작까지 완벽히 검증
- 단위 테스트와 통합 테스트 비교

  | **구분** | **단위 테스트** | **통합 테스트** |
      | --- | --- | --- |
  | 검증 범위 | 단일 클래스 또는 특정 메서드 단위 | 계층 간 협업, 데이터베이스 연동, 외부 API 통신 등 |
  | 외부 의존성 | 가짜 객체(Mock)를 활용하여 외부 요소를 완전히 격리 | 실제 물리적인 데이터베이스나 서버 환경을 구동하여 직접 연동 |
  | 수행 속도 | 메서드당 수 밀리초(ms) 단위로 극도로 빠름 | 스프링 컨테이너 기동 및 커넥션 시간으로 인해 수 초 이상 소요 |
  | 주요 목적 | 비즈니스 알고리즘의 논리적 오류 검증 | 연동 설정 결함, SQL 쿼리 오류, 트랜잭션 정합성 검증 |
- JUnit 5 라이브러리
    - 자바 생태계에서 가장 널리 사용되는 업계 표준 단위 테스트 프레임워크
    - 테스트 엔진 Jupiter 기반으로 다양한 어노테이션 및 검증용 단언(Assertions) 메소드 제공
    - 테스트 구성 단위의 분류 위계
        - 테스트 케이스: @Test 어노테이션 부여로 실제 기능의 성공/실패 여부를 독립적으로 검증하는 개별 메소드 단위
        - 테스트 클래스: 논리적으로 연관된 여러 테스트 케이스를 하나로 묶어 관리하는 자바 클래스 파일
        - 테스트 슈트: 여러 테스트 클래스나 패키지 전체를 하나의 실행 단위로 묶어 동시에 일괄 구동하는 최상위 테스트 묶음 패키지
- JUnit 주요 어노테이션 기능
    - @Test
        - 해당 메소드를 독립 실행 가능한 테스트 코드로 지정
        - 실행 버튼 활성화로 별도 메인 메소드 없이 독자 가동하며, 실제 기능 검증용 Assertions 단언 코드를 내부에 주로 작성
    - @BeforeEach
        - 테스트 메소드 실행 직전 매번 자동으로 선행할 준비 코드작성 (관습적으로 `setUp()` 명칭 사용)
        - 테스트 대상 객체를 매번 새로 생성하거나 테스트용 임시 데이터를 미리 준비라는 선처리 작업 수행
    - @AfterEach
        - 테스트 메소드 종료 직후 매번 자동으로 실행할 정리 코드 작성 (관습적으로 `tearDown()` 명칭 사용
        - 파일 입출력 후 스트림 연결 차단 또는 데이터베이스 임시 데이터 삭제 등 사후 정리 수행
    - @BeforeAll / @AfterAll
        - 전체 테스트 클래스 실행 중 처음과 끝에 단 한 번만 static으로 호출되어 실행할 공유 자원 관리 코드 작성 (관습적으로 `setUpAll() / tearDownAll()` 명칭 사용)
        - 테스트용 데이터베이스 커넥션 풀 최초 연결 또는 전체 테스트용 네트워크 커넥션 해제 등 대규모 사전/사후 작업 담당
    - @DisplayName
        - 테스트 실행 결과 창에 영어 메소드명 대신 직관적인 한글 문장으로 테스트 작업 명칭을 출력하도록 지정
        - 테스트 목적이나 시나리오 요구사항의 상세 설명을 기술하여 가독성 제고
    - @Disabled
        - 특정 테스트 메소드를 일시적으로 실행 대상으로 제외하여 생략하도록 지정
        - 개발 중인 미완성 테스트 코드가 전체 빌드를 방해하지 않도록 임시 차단하는 용도로 활용
- 주요 Assertions 검증 메소드
    - `assertEquals(expected, actual)`: 예상값과 실제값의 일치 여부 비교
    - `assertNotNull(object)`: 객체의 null 여부 검증
    - `assertTrue(condition)`: 주어진 조건식의 참(true) 여부 판별
    - `assertThrows(Exception.class, executable)`: 특정 비정상 시나리오에서 기대한 예외 발생 검증
- 테스트 메소드 명명 관례
    - 전통적인 test[메소드명] 패턴
        - 과거 JUnit 3 시절 메소드명이 test로 시작해야 작동하던 규칙에서 유래한 관행
        - 예시: `testAdd()`, `testDivideByZero()`
    - Given-When-Then 패턴
        - BDD(Behavior-Driven Development, 행동 주도 개발) 스타일의 네이밍으로, 테스트의 시나리오가 메소드명에 자연스럽게 녹아들도록 설계
        - 예시: `givenTwoNumbers_whenAdd_thenReturnsSum()`
    - [대상메소드][테스트조건][기대결과] 패턴
        - 단위 테스트 명명법 중 하나로 언더스코어( _ )를 통해 각 영역을 명확히 구분
        - 예시: `add_positiveIntegers_returnsSum()`
    - JUnit 5 @DisplayName 어노테이션 활용 권장
        - 영문 메소드명에 긴 시나리오를 작성하는 대신, 실행 결과창에 노출할 정갈한 한글 문장으로 명칭 지정
        - 예시: `@DisplayName("두 정수의 덧셈 검증")`

## 5~6교시: TDD

- TDD (Test-Driven Development)
    - 실제 동작하는 프로덕션 코드를 구현하기 전에, 해당 기능을 검증할 실패 테스트 코드를 먼저 작성하고 이를 순차적으로 통과시키며 완성해 나가는 설계 중심 개발 방법론
    - TDD 핵심 2대 원칙 (켄트 벡의 철학)
        - 오직 자동화된 테스트가 실패할 경우에만 새로운 프로덕션 코드를 작성 (테스트가 없는 코드는 작성하지 말 것)
        - 코드에 기재된 모든 형태의 중복을 철저히 제거
    - TDD 핵심 구동 3단계 사이클
        - RED (실패): 구현하고자 하는 기능 요구사항에 맞추어 반드시 실패하는 테스트 코드 우선 작성 (클래스나 메소드 설계의 첫 틀 마련)
        - GREEN (성공): 테스트를 빠르게 통과시키기 위해 최소한 단순 구현 진행 (하드코딩된 임시 반환값 활용 가능)
        - REFACTOR (개선): 테스트의 통과 상태를 깨뜨리지 않는 안전망 속에서 중복 코드 제거 및 변수 정리 등 내부 구조 정비
    - TDD 진행시 초보자를 위한 대표 전략
        - 가짜로 구현하기 (Fake it)
            - 테스트를 우선 성공시키기 위해 정답 상수나 픽스된 텍스트를 즉시 반환하게 만든 뒤, 테스트가 성공하면 점진적으로 진짜 변수와 계산식 코드로 진화시키는 전략
        - 삼각 측량법 (Triangulation)
            - 테스트 케이스를 2개 이상 연속해서 작성하여 하드코딩 형태로 작성해 둔 임시 코드가 자연스럽게 진자 일반화된 핵심 로직으로 바뀔 수밖에 없도록 만드는 전략
            - 예: 덧셈 검증 시 2와 3 입력으로 5 확인 후, 이어서 4와 5 입력으로 9 확인

    ```java
    // 1. RED 단계: 구현 클래스가 아직 부재하여 컴파일 에러 및 실행 실패를 유발
    class GreeterTest {
        @Test
        void testSayHello() {
            // 아직 Greeter 클래스가 없거나 sayHello 메서드가 비어 있어 실패
            Greeter greeter = new Greeter();
            assertEquals("Hello, Jay", greeter.sayHello("Jay"));
        }
    }
    
    // 2. GREEN 단계: 일단 테스트를 통과(초록불)시키기 위해 임시 상수값을 바로 반환
    class Greeter {
        public String sayHello(String name) {
            return "Hello, " + name; // 임시 문자열 반환으로 빠르게 성공 유도
        }
    }
    ```

- TDD 도입과 아키텍처 개선
    - 설계 도구로서의 TDD 본질
        - TDD는 오류 검출용 테스트 기술이 아닌 깔끔하고 안전한 코드를 깎아내기 위한 설계 유도 장치
    - 단일 책임 원칙(SRP)의 자연스러운 준수
        - 테스트 코드를 작성할 때 테스트 시나리오가 비정상적으로 복잡하고 길어진다면, 이는 검증 대상 클래스가 너무 많은 책임을 떠맡고 있다는 의미
        - 테스트 작성을 용이하게 만들기 위해 자연스럽게 클래스의 크기를 쪼개어 하나의 일만 전담하게 만드는 단일 책임 원칙을 적용
    - 느슨한 결합과 테스트 용이성(Testability) 확보
        - 외부 데이터베이스나 인터넷 API 연결이 끊어지면 테스트 구동이 원천 불가능해지는 모놀리식 결함을 개선하도록 유도
        - 외부 연동 통로를 인터페이스로 먼저 정의하여 추상화하고, 실제 객체 대신 임시 대역(가짜 객체 등)을 갈아 끼워 테스트가 가능하게 만들기 위해 의존성 주입 구조를 설계에 강제적으로 적용
        - 결과적으로 의존성이 한곳으로 강하게 굳어지는 하드코딩이 사라지고, 변경과 리팩토링이 매우 유연하게 대처할 수 있는 안전한 아키텍처를 형성
