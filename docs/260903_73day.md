# **스프링 선언적 트랜잭션**

- 트랜잭션 참고: https://github.com/BEBC-25/java-yong/blob/main/docs/04.database-2.md#6-트랜잭션의-이해

## **1. 스프링 트랜잭션 추상화**

### **1.1 데이터 접근 기술별 트랜잭션 관리 방식과 한계**

- 데이터 접근 기술마다 트랜잭션을 제어하는 자바 API와 사용 방식이 제각각 다름.
    - JDBC / MyBatis: `connection.setAutoCommit(false)`, `connection.commit()`, `connection.rollback()`
    - JPA: `entityManager.getTransaction().begin()`, `transaction.commit()`, `transaction.rollback()`
    - Hibernate: `session.beginTransaction()`, `tx.commit()`, `tx.rollback()`
- 스프링이 제공하는 기술별 전용 트랜잭션 매니저 클래스
    - 스프링은 이처럼 서로 다른 외부 기술들의 트랜잭션을 제어할 수 있도록 기술별 전용 구현 클래스들을 제공함.
        - `DataSourceTransactionManager`: 순수 JDBC, JdbcTemplate, Spring Data JDBC, MyBatis 전용
        - `JpaTransactionManager`: JPA 엔티티 매니저 연동 전용
        - `HibernateTransactionManager`: 하이버네이트 세션 연동 전용
- 개별 구현 클래스 직접 의존 시의 한계
    - 서비스 계층의 비즈니스 코드가 특정 트랜잭션 매니저 클래스(예: `DataSourceTransactionManager`)에 직접 의존하면, 향후 데이터 접근 기술을 변경(예: MyBatis ➔ JPA)할 때 서비스 계층의 트랜잭션 제어 코드를 수정해야 하는 문제가 남음.

### **1.2 PlatformTransactionManager를 통한 단일 표준 추상화**

- 스프링은 이 개별 구현 클래스들을 다시 하나의 최상위 표준 인터페이스인 `PlatformTransactionManager`로 통합 추상화함.

```
                         [PlatformTransactionManager 인터페이스]
                                          ▲
             ┌────────────────────────────┼────────────────────────────┐
             │                            │                            │
[DataSourceTransactionManager]   [JpaTransactionManager]    [HibernateTransactionManager]
(JDBC / JdbcTemplate / MyBatis /        (JPA 전용)                  (하이버네이트)
       Spring Data JDBC)
```

- 트랜잭션 추상화가 제공하는 핵심 이점
    - 기술 독립성 및 단일 제어: 서비스 계층은 하위의 구체적인 트랜잭션 매니저 클래스를 직접 다루지 않고 최상위 인터페이스에만 의존하므로, `@Transactional` 선언 하나만으로 모든 데이터 접근 기술의 트랜잭션을 동일하게 제어할 수 있음.
    - OCP(개방-폐쇄 원칙) 5 준수: 데이터 접근 기술을 MyBatis에서 JPA 등으로 교체하더라도 서비스 계층의 비즈니스 로직과 `@Transactional` 코드는 단 한 줄도 수정할 필요가 없음.
    - 스프링 부트 자동 구성(Auto-Configuration): 빌드 의존성(`starter`)에 따라 적절한 트랜잭션 매니저 구현체 빈을 프레임워크가 자동으로 생성하여 스프링 컨테이너에 등록함.
- 스레드 로컬 기반 커넥션 동기화 (TransactionSynchronizationManager)
    - 스프링은 멀티스레드 환경에서 각 스레드마다 독립적인 DB 커넥션을 유지하기 위해 `TransactionSynchronizationManager`(스레드 로컬(ThreadLocal) 6 저장소)를 사용함.
    - 트랜잭션 시작 시 획득한 커넥션을 스레드 로컬에 보관하고, 서비스 내부에서 호출되는 DAO, Mapper들이 동일한 커넥션을 꺼내 쓰도록 보장함.
    - 여러 매퍼 메서드나 JdbcTemplate을 동일한 서비스 메서드 안에서 호출하더라도 하나의 트랜잭션으로 묶이는 이유.

## **2. @Transactional 선언과 AOP 프록시 동작 메커니즘**

### **2.1 선언적 트랜잭션의 장점 및 적용 위치**

- 과거 트랜잭션 코드를 직접 자바 소스코드에 작성하던 프로그래밍 방식(Programmatic Transaction)과 달리, `@Transactional` 어노테이션을 메서드나 클래스에 선언하기만 하면 프레임워크가 트랜잭션 시작, 커밋, 롤백을 자동 처리함.
- 비즈니스 핵심 로직과 트랜잭션 인프라 코드를 명확히 분리하여 단일 책임 원칙(SRP) 7 을 준수함.

### **2.2 AOP 프록시를 통한 트랜잭션 경계 제어 메커니즘**

- 트랜잭션 경계(Transaction Boundary): 트랜잭션이 시작(Begin)되어 커밋(Commit) 또는 롤백(Rollback)으로 종결되는 논리적인 작업 범위를 의미하며, AOP 8 프록시가 이 경계의 시작과 끝을 가로채어 트랜잭션을 자동 제어함.
- 컨트롤러가 `@Transactional`이 부여된 서비스 빈을 호출하면, 실제 타깃 객체가 아닌 스프링이 동적으로 생성한 트랜잭션 프록시(Proxy) 객체가 호출을 인터셉트함.

```
    [컨트롤러]
        │
        ▼
[트랜잭션 AOP 프록시] ─── (1) PlatformTransactionManager.getTransaction() ───> 커넥션 획득 & setAutoCommit(false)
        │
        ├─── (2) 타깃 서비스 비즈니스 메서드 실행 ───> (MyBatis / JDBC 작업 수행)
        │
        ▼
[트랜잭션 AOP 프록시] ─── (3) 정상 종료 시: commit() / 예외 발생 시: rollback() ───> 커넥션 자원 반납
```

## **3. 트랜잭션 전파 속성과 격리 수준**

### **3.1 전파 속성 (Propagation)**

- 이미 트랜잭션이 진행 중인 상태에서 또 다른 트랜잭션 메서드가 호출되었을 때, 기존 트랜잭션에 참여할지 혹은 새로운 독립 트랜잭션을 시작할지 결정하는 정책.

| **전파 속성** | **동작 방식** | **주요 활용처** |
| --- | --- | --- |
| `REQUIRED` (기본값) | 기존 트랜잭션이 존재하면 참여하고, 없으면 새로운 트랜잭션을 생성함 | 대부분의 일반적인 비즈니스 로직 |
| `REQUIRES_NEW` | 항상 독립적인 새로운 트랜잭션을 시작함 (기존 트랜잭션은 일시 보류됨) | 실패해도 메인 트랜잭션에 영향을 주지 않아야 하는 감사 로그, 알림 발송 |
| `SUPPORTS` | 기존 트랜잭션이 있으면 참여하고, 없으면 트랜잭션 없이 일반 모드로 동작함 | 단순 데이터 조회 작업 |
| `NOT_SUPPORTED` | 기존 트랜잭션이 있어도 보류시키고, 트랜잭션 없이 동작함 | 외부 API 연동 등 장시간 블로킹 작업 |
| `MANDATORY` | 반드시 기존 트랜잭션이 존재해야 하며, 없으면 예외(`IllegalTransactionStateException`) 발생 | 독립 실행을 금지하는 하위 컴포넌트 |
| `NEVER` | 트랜잭션이 없어야 하며, 기존 트랜잭션이 존재하면 예외 발생 | 트랜잭션 비허용 작업 |

### **3.2 격리 수준 (Isolation)**

- 참고: https://github.com/BEBC-25/java-yong/blob/main/docs/04.database-2.md#625-데이터베이스-격리-수준-isolation-level
- 여러 트랜잭션이 동시에 실행될 때 특정 트랜잭션이 다른 트랜잭션의 변경 데이터를 볼 수 있는 허용 범위를 규정함.

| **격리 수준** | **동시성 처리 성능** | **격리 안전성** | **발생 가능한 이상 현상** |
| --- | --- | --- | --- |
| `READ_UNCOMMITTED` | 가장 빠름 | 가장 낮음 | Dirty Read, Non-Repeatable Read, Phantom Read |
| `READ_COMMITTED` | 우수함 | 보통 | Non-Repeatable Read, Phantom Read |
| `REPEATABLE_READ` (MySQL InnoDB 기본값) | 보통 | 높음 | Phantom Read (InnoDB MVCC 환경에서는 대부분 방지) |
| `SERIALIZABLE` | 가장 느림 | 우수함 | 모든 이상 현상 방지 (트랜잭션 순차 직렬 실행) |
- 동시성 격리 이상 현상
    - Dirty Read: 아직 커밋되지 않은 다른 트랜잭션의 임시 변경 데이터를 읽는 현상.
    - Non-Repeatable Read: 동일한 트랜잭션 내에서 같은 쿼리를 두 번 실행했을 때, 중간에 다른 트랜잭션이 데이터를 수정/커밋하여 조회 결과값이 달라지는 현상.
    - Phantom Read: 동일한 범위 조건으로 두 번 조회했을 때, 중간에 다른 트랜잭션이 새로운 행을 삽입/삭제하여 결과 행 수가 달라지는 현상.

### **3.3 readOnly 속성을 통한 조회 성능 최적화**

- 데이터 변경(INSERT, UPDATE, DELETE) 없이 단순 조회만 수행하는 메서드에는 `@Transactional(readOnly = true)`를 선언함.
- 최적화 효과
    - JDBC 드라이버 및 DB 커넥션이 읽기 전용 모드로 전환되어 불필요한 쓰기 락(Lock) 경합 방지.
    - JPA 및 ORM 환경에서 변경 감지(Dirty Checking)를 위한 스냅샷 객체를 메모리에 보관하지 않아 CPU 및 메모리 자원 절약.
    - 데이터 변경 쿼리 실행 시 예외를 발생시켜 의도치 않은 데이터 조작을 차단.

## **4. @Transactional 실무 사용법과 권장 설정**

- 일반적으로 트랜잭션 경계는 비즈니스 로직의 단위가 시작되고 종결되는 서비스(Service) 계층에 적용함.
- 기본 선언 방식
    - 스프링의 `@Transactional`은 별도의 옵션을 주지 않아도 가장 표준적이고 안전한 기본값(전파: REQUIRED, 격리수준: DB 기본값)으로 동작함.
    - 데이터 등록, 수정, 삭제 작업을 수행하는 비즈니스 메서드 상단에 `@Transactional`을 선언.
- 적용 위치 및 우선순위 규칙
    - 클래스 레벨 선언: 클래스 내의 모든 `public` 메서드에 기본 트랜잭션이 적용됨.
    - 메서드 레벨 선언: 개별 메서드에 선언되며, 클래스 레벨보다 더 높은 우선순위를 가짐 (클래스 설정을 오버라이드함).
- 실무에서 주로 사용하는 핵심 속성 2가지
    - `readOnly = true` (조회 성능 최적화): 데이터 변경이 없는 단순 조회 메서드에 선언하며, 불필요한 DB 쓰기 락(Lock)을 방지하고 메모리 자원을 절약함.
    - `rollbackFor = Exception.class` (예외 롤백 보장): 스프링은 기본적으로 언체크 예외(`RuntimeException`)만 자동 롤백하고 체크 예외(`Exception`)는 커밋하므로, 실무에서는 모든 예외 상황에서 안전하게 롤백되도록 `rollbackFor = Exception.class`를 명시함.
        - Exception 참고: https://github.com/BEBC-25/java-yong/blob/main/docs/05.java_advanced.md#12-예외-클래스의-계층-구조
- 실무 모범 패턴
    - 서비스 클래스 상단에 `@Transactional(readOnly = true)`를 선언하여 기본 조회 성능을 최적화하고, 데이터 변경(INSERT, UPDATE, DELETE)이 필요한 메서드에만 `@Transactional(rollbackFor = Exception.class)`를 부여함.

```java
@Service
@Transactional(readOnly = true) // 클래스 전체(모든 메서드에 적용): 기본 조회 전용 모드로 성능 최적화
public class PostService {

    private final PostMapper postMapper;
    private final LikeBookmarkMapper likeBookmarkMapper;

    public PostService(PostMapper postMapper, LikeBookmarkMapper likeBookmarkMapper) {
        this.postMapper = postMapper;
        this.likeBookmarkMapper = likeBookmarkMapper;
    }

    // 1. 클래스의 기본값 readOnly = true 적용 (단순 조회)
    public PostResponseDto getPost(Long id) {
        return postMapper.findById(id);
    }

    // 2. 기본 @Transactional 적용: 별도 옵션 없이 기본값(readOnly = false, 쓰기 허용)으로 동작
    @Transactional
    public void createPost(PostCreateDto dto) {
        postMapper.insertPost(dto);
    }

    // 3. @Transactional(rollbackFor = Exception.class) 적용: 다중 작업 묶음 및 모든 예외 롤백 보장
    @Transactional(rollbackFor = Exception.class)
    public void addLike(Long memberId, Long postId) {
        // 1) 좋아요 테이블에 등록
        likeBookmarkMapper.insertLike(memberId, postId);

        // 2) post 테이블의 like_count 1 증가 (2번 작업 중 오류 발생 시 1번 좋아요 등록도 함께 롤백됨)
        postMapper.increaseLikeCount(postId);
    }
}
```

# **서비스 계층 선언적 트랜잭션 실습**

## **1. 트랜잭션 적용 시나리오: 좋아요 토글**

- 사용자가 좋아요 버튼을 클릭할 때마다 현재 상태를 반전(미등록 시 등록, 기등록 시 취소)시키는 토글(Toggle) 시나리오.
- 작업 도중 예외가 발생하면 앞선 모든 데이터 변경 연산이 원자적으로 롤백되어 데이터 불일치를 방지함.

### **1.1 좋아요 토글 단계별 실행 흐름**

1. 대상 게시글 존재 여부 검증 (`PostMapper.findById`)
2. 현재 회원의 기존 좋아요 등록 여부 조회 (`PostLikeMapper.countLike`)
3. 조회 결과에 따른 상태 분기 및 복합 연산 실행
- 미등록 상태인 경우: `post_like` 테이블에 좋아요 등록(`insertLike`) 및 `post` 테이블의 `like_count` 1 증가(`increaseLikeCount`)를 원자적으로 수행하고, 갱신된 결과 DTO(`liked: true`, 최신 `likeCount`) 반환
- 기등록 상태인 경우: `post_like` 테이블에서 좋아요 삭제(`deleteLike`) 및 `post` 테이블의 `like_count` 1 감소(`decreaseLikeCount`)를 원자적으로 수행하고, 갱신된 결과 DTO(`liked: false`, 최신 `likeCount`) 반환

## **2. 매퍼 설계 원칙: 도메인 관점과 테이블 책임 분리**

### **2.1 도메인 관점 (통합 매퍼)**

- 특징: 게시글(Post)이라는 핵심 도메인 개체와 생명주기를 함께하는 부속 데이터(`post_like`, `post_comment` 등)의 쿼리를 `PostMapper` 단일 파일에 모두 모아 관리함.
- 장점: 관련 기능의 쿼리가 한곳에 집중되어 파일 개수가 적고 초기 도메인 흐름 파악이 수월함.
- 단점: 기능이 늘어날수록 단일 XML 파일이 지나치게 길어지고, 좋아요나 댓글 같은 다른 테이블의 쿼리를 고치다가 게시글 기본 쿼리에 의도치 않은 영향을 줄 수 있어 코드 관리가 복잡해짐.

### **2.2 테이블 책임 분리 관점 (독립 매퍼)**

- 특징: 데이터베이스의 개별 물리 테이블 1개당 매퍼 1개를 원칙으로 하여, `post` 테이블 전담 매퍼(`PostMapper`)와 `post_like` 테이블 전담 매퍼(`PostLikeMapper`)로 명확히 분리함.
- 장점: 단일 책임 원칙(SRP) 72 을 준수하여 각 매퍼가 특정 테이블에 대한 데이터 접근만 전담하므로 결합도가 낮아지고 유지보수 및 모듈화가 용이함.
- 단점: 관리해야 할 매퍼 인터페이스와 XML 매퍼 파일의 총 개수가 늘어남.

### **5.3 서비스 구현 클래스**

- `PostMapper`와 `PostLikeMapper` 2개의 분리된 매퍼를 주입받아, 하나의 `@Transactional(rollbackFor = Exception.class)` 경계 안에서 상태 확인 및 조건 분기 변경 연산을 원자적으로 실행함.
- `PostResponseDto`에 누락되었던 likeCount 필드 추가 후 `PostMapperTest` 테스트 실행
    - 테스트가 실패한 원인 분석 후 오류 수정
- src/main/java/net/likelion/bebc25/sns/service/PostLikeServiceImpl.java

    ```java
    package net.likelion.bebc25.sns.service;
    
    import net.likelion.bebc25.sns.dto.LikeToggleResponseDto;
    import net.likelion.bebc25.sns.dto.PostResponseDto;
    import net.likelion.bebc25.sns.mapper.PostLikeMapper;
    import net.likelion.bebc25.sns.mapper.PostMapper;
    import org.springframework.stereotype.Service;
    import org.springframework.transaction.annotation.Transactional;
    
    @Service
    @Transactional(readOnly = true)
    public class PostLikeServiceImpl implements PostLikeService {
    
        private final PostMapper postMapper;
        private final PostLikeMapper postLikeMapper;
    
        public PostLikeServiceImpl(PostMapper postMapper, PostLikeMapper postLikeMapper) {
            this.postMapper = postMapper;
            this.postLikeMapper = postLikeMapper;
        }
    
        @Override
        @Transactional(rollbackFor = Exception.class)
        public LikeToggleResponseDto toggleLike(Long memberId, Long postId) {
            // 1. 대상 게시글 존재 여부 검증 (PostMapper)
            PostResponseDto post = postMapper.findById(postId);
            if (post == null) {
                throw new IllegalArgumentException("존재하지 않는 게시글입니다. ID: " + postId);
            }
    
            // 2. 현재 회원의 좋아요 등록 여부 확인 (PostLikeMapper)
            boolean isLiked = postLikeMapper.countLike(memberId, postId) > 0;
    
            if (isLiked) {
                // 기등록 상태: 좋아요 취소 (삭제) 및 like_count 1 감소
                postLikeMapper.deleteLike(memberId, postId);
                postMapper.decreaseLikeCount(postId);
                return new LikeToggleResponseDto(false, post.likeCount() - 1);
            } else {
                // 미등록 상태: 좋아요 등록 및 like_count 1 증가
                postLikeMapper.insertLike(memberId, postId);
                postMapper.increaseLikeCount(postId);
                return new LikeToggleResponseDto(true, post.likeCount() + 1);
            }
        }
    }
    ```


## **6. 트랜잭션 롤백 테스트 및 무결성 검증**

- 통합 테스트 환경에서 분리된 두 매퍼 간의 연동과 트랜잭션 원자성을 검증함.
- `@MockitoSpyBean`
    - 스프링 컨텍스트에 등록된 실제 빈(Bean)을 그대로 유지하면서, 원하는 특정 메서드만 가짜 동작(모킹)을 수행하거나 강제 예외를 던지도록 감싸는 테스트 어노테이션.
    - 정상적인 DB 조회/등록 동작은 실제 빈에 그대로 위임하고, 2단계인 `increaseLikeCount` 메서드 호출 시점에만 인위적인 런타임 예외를 발생시켜 시스템 장애 상황을 시뮬레이션함.
    - 검증 목적: 2단계에서 예외가 발생했을 때 `@Transactional`에 의해 앞선 1단계(좋아요 등록) 데이터까지 원자적으로 함께 롤백되는지 확인.
- `Propagation.NOT_SUPPORTED` 전파 속성
    - 동작 메커니즘: 이미 진행 중인 활성 트랜잭션이 존재하면 이를 일시 중단(Suspend)시키고, 트랜잭션이 적용되지 않는 비트랜잭션(Non-Transactional) 상태로 메서드를 실행함.
    - 적용 이유: 클래스 레벨의 `@Transactional`에 의해 생성된 부모 트랜잭션을 일시 중단하여, 서비스 메서드가 부모 트랜잭션에 참여하지 않고 독자적인 트랜잭션을 시작하도록 격리함. 그 결과 서비스 계층에서 예외가 발생하는 즉시 스스로 물리적 롤백을 완료하므로 DB의 롤백 결과를 정확히 검증할 수 있음.

## **3. 서비스 구현 클래스 및 비즈니스 예외 처리**

- `PostMapper`를 주입받아 데이터 접근 연산을 수행하며, 읽기 전용 트랜잭션 최적화와 CUD 데이터 변경 트랜잭션을 분리하여 적용.
- 클래스 레벨에 `@Transactional(readOnly = true)`를 적용하여 기본 조회 성능을 최적화하고, 데이터 변경 메서드에만 쓰기 전용 `@Transactional`을 선언함.
- 수정 및 삭제 시 대상 게시글 존재 여부를 사전에 검증하여 데이터 무결성을 보호함.
- src/main/java/net/likelion/bebc25/sns/service/PostServiceImpl.java

    ```java
    package net.likelion.bebc25.sns.service;
    
    import net.likelion.bebc25.sns.dto.PostCreateDto;
    import net.likelion.bebc25.sns.dto.PostDetailResponseDto;
    import net.likelion.bebc25.sns.dto.PostResponseDto;
    import net.likelion.bebc25.sns.dto.PostSearchCondition;
    import net.likelion.bebc25.sns.dto.PostUpdateDto;
    import net.likelion.bebc25.sns.mapper.PostMapper;
    import org.springframework.stereotype.Service;
    import org.springframework.transaction.annotation.Transactional;
    
    import java.util.List;
    
    @Service
    @Transactional(readOnly = true)
    public class PostServiceImpl implements PostService {
    
        private final PostMapper postMapper;
    
        public PostServiceImpl(PostMapper postMapper) {
            this.postMapper = postMapper;
        }
    
        @Override
        @Transactional(rollbackFor = Exception.class)
        public Long createPost(PostCreateDto dto) {
            postMapper.save(dto);
            return dto.getId();
        }
    
        @Override
        public PostResponseDto getPostById(Long id) {
            PostResponseDto post = postMapper.findById(id);
            if (post == null) {
                throw new IllegalArgumentException("존재하지 않는 게시글입니다. ID: " + id);
            }
            return post;
        }
    
        @Override
        public PostDetailResponseDto getPostDetailById(Long id) {
            PostDetailResponseDto detail = postMapper.findPostDetailById(id);
            if (detail == null) {
                throw new IllegalArgumentException("존재하지 않는 게시글입니다. ID: " + id);
            }
            return detail;
        }
    
        @Override
        public List<PostResponseDto> searchPosts(PostSearchCondition condition) {
            return postMapper.searchPosts(condition);
        }
    
        @Override
        @Transactional(rollbackFor = Exception.class)
        public void updatePost(Long id, PostUpdateDto dto) {
            // 수정 대상 게시글 존재 여부 사전 검증
            if (postMapper.findById(id) == null) {
                throw new IllegalArgumentException("수정할 게시글이 존재하지 않습니다. ID: " + id);
            }
            postMapper.update(id, dto.content(), dto.imageUrl());
        }
    
        @Override
        @Transactional(rollbackFor = Exception.class)
        public void deletePost(Long id) {
            // 삭제 대상 게시글 존재 여부 사전 검증
            if (postMapper.findById(id) == null) {
                throw new IllegalArgumentException("삭제할 게시글이 존재하지 않습니다. ID: " + id);
            }
            postMapper.deleteById(id);
        }
    
        @Override
        @Transactional(rollbackFor = Exception.class)
        public void deletePosts(List<Long> idList) {
            if (idList == null || idList.isEmpty()) {
                throw new IllegalArgumentException("삭제할 게시글 ID 목록이 비어있습니다.");
            }
            postMapper.deleteByIds(idList);
        }
    }
    ```
