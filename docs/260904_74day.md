# **웹 렌더링 패러다임의 변화**

## **1. SSR과 CSR의 동작 메커니즘**

### **1.1 전통적인 서버 사이드 렌더링(SSR) 방식의 특성**

- 이전까지 학습한 전통적인 웹 MVC(Thymeleaf) 환경에서는 백엔드 서버가 데이터베이스 조회 결과와 HTML 템플릿을 결합하여 완성된 웹 페이지(HTML 코드)를 클라이언트에 응답함.
- 웹 브라우저는 서버가 완성하여 전달해 준 HTML을 화면에 표시하는 출력 창구 역할을 수행하며, 링크를 누르거나 폼을 제출할 때마다 페이지 전체를 새로고침(Full Page Reload)하여 새로운 HTML을 수신함.

### **1.2 현대적인 클라이언트 사이드 렌더링(CSR) 방식의 특성**

- 모바일 환경의 확산과 프론트엔드 프레임워크(React, Vue, 모바일 네이티브 앱)의 등장으로 인해 화면 렌더링의 주체가 서버에서 클라이언트로 이동함.
- 백엔드 서버는 더 이상 UI 화면(HTML)을 제작하지 않고 순수한 데이터(자원, 주로 JSON 포맷)만을 응답하며, 화면 디자인과 UI를 만드는 작업은 클라이언트 애플리케이션이 전담함.
- 화면 전체를 다시 불러오지 않고 필요한 데이터만 백그라운드 비동기 통신(Fetch, Axios)을 통해 받아와 동적으로 화면을 갱신하므로, 깜빡임 없이 유려한 사용자 경험(UX)을 제공함.

### **1.3 분리된 환경에서 요구되는 데이터 통신 규격의 핵심 요건**

#### **1) 플랫폼 및 프로그래밍 언어의 독립성**

- 웹 브라우저(JavaScript/TypeScript), 스마트폰 앱(Swift, Kotlin), 데스크톱 애플리케이션 등 클라이언트 환경마다 사용하는 언어와 실행 런타임이 서로 상이함.
- 특정 언어나 플랫폼에 종속되지 않고 누구나 쉽게 해석할 수 있는 범용 텍스트 데이터 포맷(JSON 등)과 표준 전송 방식이 요구됨.

#### **2) 직관적인 자원 식별과 작업 의도 전달 체계**

- 복잡한 내부 함수를 직접 호출하는 방식 대신, 다루고자 하는 대상(자원 데이터)을 고유한 주소 체계로 식별하고 수행할 작업(CRUD - 등록, 조회, 수정, 삭제)을 누구나 알기 쉬운 표준적인 방식으로 명시할 수 있어야 함.

#### **3) 기존 웹 표준 인프라(인터넷 네트워크망)의 그대로 재활용**

- 별도의 전용 통신망 구축이나 특수 소프트웨어 설치 없이, 전 세계 인터넷에 이미 검증되어 구축된 HTTP 프로토콜 및 네트워크 가속 장비(캐시, 프록시, 로드밸런서)를 변경 없이 활용할 수 있어야 함.

#### **4) 표준 통신 아키텍처로서의 귀결**

- 이처럼 화면과 데이터가 분리된 환경에서 요구되는 언어 독립성, 직관적인 자원 식별, 웹 인프라 재활용이라는 조건을 충실하게 충족하며 현대 웹 통신의 표준으로 자리 잡은 아키텍처 스타일이 바로 REST(Representational State Transfer) 방식.

## **2. 데이터 중심 아키텍처에서의 클라이언트와 서버 역할**

### **2.1 클라이언트의 역할**

- 자원 식별과 수행 행위의 명확한 전달
- 클라이언트는 원하는 대상 데이터를 명확한 명사형 URI(예: `/posts/10`)로 식별하여 요청
- 수행하고자 하는 작업의 의도(CRUD - 등록, 조회, 수정, 삭제)에 맞게 표준 HTTP 메서드(`POST`, `GET`, `PUT/PATCH`, `DELETE` 등)를 정확하게 구분하여 서버로 전송

### **2.2 서버의 역할**

- 서버는 클라이언트 요청의 유효성을 검증하고 비즈니스 로직을 수행한 후, UI가 아닌 순수한 데이터(자원)를 JSON 같은 표준화된 포맷으로 응답
- 처리 결과의 성공이나 실패를 명확히 알리기 위해 표준 HTTP 응답 상태 코드(`200 OK`, `201 Created`, `400 Bad Request`, `404 Not Found` 등)를 올바르게 회신

### **2.3 관심사 분리를 통한 다중 플랫폼 확장**

- 백엔드 서버가 화면 렌더링에서 완전히 분리됨으로써, 하나의 동일한 REST API 서버로 웹 브라우저는 물론 iOS/Android 모바일 앱, 스마트 TV, 외부 서드파티 시스템 등 다양한 클라이언트를 동시에 수용할 수 있는 확장성을 확보

## **3. SSR과 CSR 렌더링 아키텍처 비교**

| **비교 항목** | **전통적 SSR 방식 (Spring MVC + Thymeleaf)** | **현대적 CSR 방식 (Spring Boot REST API + React)** |
| --- | --- | --- |
| 서버 응답 데이터 | 완성된 HTML 코드 (데이터와 화면 레이아웃 결합) | 순수한 자원 데이터 (주로 JSON 포맷) |
| 화면 렌더링 주체 | 백엔드 서버 (ViewResolver 및 템플릿 엔진) | 프론트엔드 클라이언트 (브라우저 자바스크립트 엔진) |
| 화면 전환 메커니즘 | 페이지 전체 새로고침 (MPA 8 구조) | 필요한 데이터만 비동기 갱신 (SPA 9 구조) |
| 클라이언트-서버 결합도 | 화면 템플릿과 백엔드 컨트롤러 간의 강한 결합 | 표준 HTTP 프로토콜과 JSON 기반의 완전한 독립 분리 |
| 다중 플랫폼 지원 | 웹 브라우저 화면 출력에 한정됨 | 단일 API로 웹, 모바일 앱, 스마트 워치 등 다중 플랫폼 동시 연동 |

> [!NOTE]
> 화면과 데이터가 분리된 현대적인 웹 환경(CSR)을 성공적으로 구축하기 위해서는 클라이언트와 서버가 서로 혼선 없이 데이터를 주고받을 수 있는 정교한 설계 규칙이 필요하며, 전 세계 소프트웨어 생태계가 공통으로 채택한 표준 규칙이 바로 REST 아키텍처.

# **REST 아키텍처와 설계 원칙**

## **1. REST 핵심 용어 정의**

- REST(Representational State Transfer): 웹의 기본 통신 표준(HTTP 프로토콜)을 그대로 활용하여, URI로는 자원을 식별하고 HTTP 메서드로는 행위를 표현함으로써 서로 다른 분산 시스템 간에 데이터를 원활하게 주고받도록 정의한 아키텍처 설계 원칙.
- RESTful: REST 아키텍처의 설계 원칙과 제약조건을 충실하게 준수하여 구현한 웹 서비스를 수식하는 형용사적 표현으로, "REST 규칙을 올바르게 따르는 시스템"을 통칭함.
- REST API: REST 설계 원칙을 기반으로 구현한 애플리케이션 프로그래밍 인터페이스로, 클라이언트가 HTTP 표준 요청(URI와 메서드)을 통해 서버의 데이터와 비즈니스 로직을 원격으로 호출하고 응답을 수신하는 웹 통신 인터페이스.

## **2. REST 아키텍처 6대 제약조건**

- 클라이언트-서버 구조 (Client-Server Architecture): 사용자 인터페이스(UI)를 담당하는 클라이언트와 데이터 저장 및 비즈니스 로직을 담당하는 서버의 관심사를 완전히 분리하여 각 계층의 독립적 진화를 보장함.
- 무상태성 (Statelessness): 서버는 클라이언트의 이전 요청 상태(세션 등)를 저장하지 않으며, 클라이언트가 보내는 모든 요청은 해당 작업을 처리하는 데 필요한 모든 정보를 자체적으로 포함해야 함.
- 캐시 가능성 (Cacheability): 클라이언트는 서버의 응답을 캐싱할 수 있어야 하며, HTTP 표준 캐시 헤더(Cache-Control 등)를 통해 네트워크 대역폭을 절약하고 응답 속도를 향상시킴.
- 계층화 시스템 (Layered System): 클라이언트는 대상 서버에 직접 연결되었는지 아니면 중간 프록시, 로드밸런서, 게이트웨이 등을 거치는지 알 수 없으며, 보안과 로드밸런싱 등 중간 계층을 유연하게 추가할 수 있음.
- 균일한 인터페이스 (Uniform Interface): 표준 URI를 통한 명확한 자원 식별과 표준 HTTP 메서드를 통한 일관된 자원 조작 규칙을 준수하여 플랫폼에 독립적인 통신을 수행함.
- 주문형 코드 (Code on Demand, 선택적): 서버가 클라이언트에게 실행 가능한 코드(JavaScript 등)를 전송하여 클라이언트 기능을 확장할 수 있음.

## **3. REST 환경의 HTTP 메서드 매핑**

- 전통적인 HTML 폼(Form) 환경의 제약
    - 웹 브라우저의 기본 `<form>` 태그는 `GET`과 `POST`만 전송할 수 있어 수정이나 삭제 시에도 `/posts/update`, `/posts/delete`처럼 URI에 행위 동사를 포함하여 처리해야 했음.
- REST 환경에서의 완전한 CRUD 메서드 매핑
    - 클라이언트가 비동기 HTTP 통신을 직접 제어하므로, 동일한 명사형 URI(예: `/api/v1/posts/1`)에 대해 HTTP 메서드(`GET`, `POST`, `PUT`, `PATCH`, `DELETE`)만으로 명확하게 CRUD 행위를 분리함.
- 요청 본문(Body) 데이터 포맷의 다양성
    - REST 요청 본문은 JSON(`application/json`)에 국한되지 않으며, 파일 업로드를 위한 `multipart/form-data`, 폼 데이터 전송을 위한 `application/x-www-form-urlencoded`, `application/xml` 등 `Content-Type` 헤더에 지정된 다양한 미디어 타입을 목적에 맞게 전송함.

# **RESTful URI 설계와 HTTP 상태 코드**

- HTTP 프로토콜 참고: 스프링 MVC 웹 개발 기초 - 2. HTTP 프로토콜

## **1. 자원 중심의 URI 설계 표준**

### **1.1 URI 설계 핵심 원칙**

#### **1) 자원은 동사 대신 명사 복수형(Plural Nouns) 사용**

- 자원의 집합을 나타내기 위해 명사 복수형을 사용함.
- 올바른 예: `/posts`, `/members`, `/comments`
- 잘못된 예: `/post`, `/getPosts`, `/createPost`

#### **2) 행위는 URI에 포함하지 않고 HTTP 메서드로 표현**

- URI 경로에 CRUD 행위 명칭을 포함하지 않고 HTTP 요청 메서드로 역할을 분리함.
- 올바른 예: `GET /posts/1`, `DELETE /posts/1`
- 잘못된 예: `GET /posts/get/1`, `POST /posts/delete/1`

#### **3) 하위 자원 간의 계층적 연관관계 표현**

- 특정 게시글에 속한 댓글 목록을 조회할 때 슬래시(/)를 활용해 상하위 포함 관계를 표현함.
- 올바른 예: `GET /posts/10/comments`, `POST /posts/10/comments`

#### **4) 소문자 사용 및 하이픈(-) 케이스 권장**

- URI 경로에는 대문자를 지양하고 소문자를 기본으로 적용함.
- 단어 조합 시 카멜 케이스나 언더스코어(_) 대신 케밥 케이스(하이픈 )를 적용함.
- 올바른 예: `/post-likes`, `/member-profiles`
- 잘못된 예: `/post_likes`, `/postLikes`

#### **5) 마지막 슬래시(Trailing Slash) 제거**

- 혼란을 방지하기 위해 경로 끝에 불필요한 슬래시를 붙이지 않음.
- 올바른 예: `/posts/10`
- 잘못된 예: `/posts/10/`

#### **6) 필터링, 정렬, 페이징은 쿼리 파라미터(Query String) 활용**

- 자원의 개별 식별(단건 조회)에는 경로 변수를 사용하고, 목록 조회 시 조건 필터링, 정렬, 페이징 데이터는 URI 경로 대신 쿼리 파라미터를 활용함.
- 올바른 예: `GET /posts?category=tech&sort=createdAt,desc&page=0&size=10`, `GET /posts?keyword=spring`
- 잘못된 예: `GET /posts/category/tech/sort/desc`, `GET /getTechPosts`

## **2. 주요 HTTP 응답 상태 코드**

| **상태 코드** | **식별 명칭** | **발생 시점 및 의미** | **적용 시나리오** |
| --- | --- | --- | --- |
| `200` | OK | 클라이언트의 요청이 정상 처리됨 | 데이터 조회, 수정 성공 |
| `201` | Created | 요청이 성공하여 새로운 자원이 생성됨 | 신규 게시글 등록 성공 (`Location` 헤더에 신규 URI 반환) |
| `204` | No Content | 요청이 성공했으나 반환할 본문 데이터가 없음 | 데이터 삭제 완료 |
| `400` | Bad Request | 클라이언트의 요청 데이터 포맷이나 유효성 검증 실패 | 필수 필드 누락, DTO 유효성 검증 실패 |
| `401` | Unauthorized | 인증 11 (Authentication) 정보가 없거나 유효하지 않음 | 미로그인 상태의 API 요청, 만료된 JWT 12 토큰 |
| `403` | Forbidden | 인증 11² 은 완료되었으나 해당 자원에 대한 인가 13 (Authorization) 권한 부족 | 타인의 게시글 수정/삭제 시도 |
| `404` | Not Found | 요청한 URI에 해당하는 자원이 서버에 존재하지 않음 | 존재하지 않는 ID로 게시글 조회 요청 |
| `405` | Method Not Allowed | 요청한 URI는 존재하지만 지원하지 않는 HTTP 메서드를 사용함 | POST 전용 엔드포인트에 GET 또는 PUT 요청 |
| `409` | Conflict | 서버의 현재 상태와 충돌하여 요청을 수행할 수 없음 | 회원가입 시 중복된 이메일이나 아이디 제출 |
| `500` | Internal Server Error | 서버 내부 처리 중 예측하지 못한 시스템 예외 발생 | 데이터베이스 접속 장애, NPE 발생 |

# **Spring REST 컨트롤러와 메시지 변환**

## **1. @RestController의 구조와 동작 메커니즘**

- 스프링 MVC 컨트롤러 참고: 스프링 MVC 웹 개발 기초- 4. Spring MVC 컨트롤러 설계 및 웹 요청 핸들러 정의
- `@Controller`: 전통적인 웹 MVC에서 뷰 템플릿(Thymeleaf)의 이름을 문자열로 반환하여 ViewResolver가 HTML 화면을 렌더링하도록 제어함.
- `@ResponseBody`: 메서드의 반환값을 뷰(HTML)로 전달하지 않고, 반환한 데이터가 HTTP 응답 본문(Body)에 직접 사용됨.
- `@RestController`: `@Controller`와 `@ResponseBody`가 결합된 편의용 합성 어노테이션으로, 클래스 내의 모든 핸들러 메서드에 `@ResponseBody`를 일괄 적용하여 자바 객체 데이터를 직접 직렬화 14 하여 HTTP 응답 본문에 JSON 포맷으로 출력함.
- Spring Web 스타터 의존성 확인 (`build.gradle`)
    - `@RestController`, `HttpMessageConverter`, Jackson 15 `ObjectMapper` 등 REST API 구현에 필요한 핵심 기능은 `spring-boot-starter-web` 스타터에 기본 포함되어 제공됨.

        ```
        dependencies {
            // Spring MVC 및 Jackson 라이브러리가 기본 포함된 웹 스타터
            implementation 'org.springframework.boot:spring-boot-starter-web'
        }
        ```


## **2. HttpMessageConverter와 Jackson 직렬화**

### **2.1 자바 객체의 네트워크 전송 한계와 JSON 변환의 필요성**

- 메모리 참조의 한계: 자바 객체는 JVM(Java Virtual Machine) 힙(Heap) 메모리에 상주하는 이진 데이터로, 특정 프로세스의 메모리 주소 체계 안에서만 유효하므로 네트워크 통신시 그대로 전송할 수 없음.
- 이기종 환경 간의 언어 장벽: 클라이언트(웹 브라우저의 JavaScript, 모바일 앱의 Swift나 Kotlin 등)는 자바 고유의 객체 구조나 바이트코드를 직접 해석할 수 없음.
- 표준 데이터 교환 포맷으로서의 JSON: 서로 다른 시스템 간에 데이터를 주고받기 위해서는 모든 플랫폼과 프로그래밍 언어가 공통으로 읽고 쓸 수 있는 텍스트 규격이 필요하며, 가볍고 직관적인 키-값(Key-Value) 구조의 JSON 포맷이 사실상 표준으로 활용됨.

### **2.2 HttpMessageConverter의 역할과 구조**

- `HttpMessageConverter`는 HTTP 요청 본문과 응답 본문의 다양한 미디어 타입 변환 규격을 정의한 스프링 MVC의 표준 인터페이스.
- 스프링은 바이트 배열, 단순 문자열, JSON 등 지원 포맷별로 여러 변환기 구현체 목록을 등록하여 관리함.
- 클라이언트가 `application/json` 포맷으로 요청하거나 응답을 요구할 때, 스프링은 `HttpMessageConverter` 인터페이스의 실제 JSON 구현 클래스인 `MappingJackson2HttpMessageConverter`를 선택하여 직렬화 14² 및 역직렬화 16 작업을 위임함.

### **2.3 요청 본문 역직렬화 메커니즘**

- 클라이언트가 요청 헤더에 `Content-Type: application/json`을 명시하거나 헤더를 생략한 경우, 스프링 MVC의 메시지 컨버터 탐색 규칙에 따라 기본 등록된 `MappingJackson2HttpMessageConverter`가 동작함.
- 내부적으로 Jackson `ObjectMapper`를 사용하여 HTTP 요청 본문의 JSON 문자열을 파싱하고, `@RequestBody`가 선언된 매개변수 타입(Record 또는 DTO 객체)으로 역직렬화하여 주입함.
- 클라이언트 HTTP 요청 본문 (JSON 문자열)

    ```json
    {
      "memberId": 1,
      "content": "REST API",
      "imageUrl": "https://example.com/img/spring.png"
    }
    ```

- 컨트롤러 핸들러 메서드 (@RequestBody를 통한 역직렬화 주입)

    ```java
    @PostMapping("/posts")
    public void createPost(@RequestBody PostCreateRequest request) {
        // 요청 바디의 JSON 문자열이 PostCreateRequest 객체로 역직렬화 되어서 객체로 전달됨
        // ...
    }
    ```


### **2.4 응답 본문 직렬화 메커니즘**

- 핸들러 메서드가 자바 객체(또는 `ResponseEntity<T>`)를 반환하면 스프링 MVC의 콘텐츠 협상(Content Negotiation) 메커니즘이 동작함.
- 클라이언트가 `Accept: application/json`을 명시하거나 헤더를 생략(`/*`)한 경우, 기본 등록된 `MappingJackson2HttpMessageConverter`가 우선 채택되어 동작함.
- 내부의 Jackson `ObjectMapper`가 자바 객체를 규격화된 JSON 텍스트로 직렬화하여 HTTP 응답 본문 출력 스트림에 기록함.
- 컨트롤러 핸들러 메서드 (자바 Record 객체 반환)

    ```java
    @GetMapping("/posts/{id}")
    public ResponseEntity<PostResponse> getPost(@PathVariable("id") Long id) {
        PostResponse response = postService.getPostById(id);
        return ResponseEntity.ok(response); // 응답 상태 코드 200번으로 response 객체를 JSON 문자열로 직렬화하여 전송
    }
    ```

- 클라이언트 HTTP 응답 본문 (직렬화된 JSON 텍스트)

    ```json
    {
      "id": 1,
      "memberId": 1,
      "content": "스프링 부트 4와 MyBatis 연동 실습 중입니다! 매퍼 XML과 동적 SQL 바인딩이 생각보다 매우 강력하네요.",
      "imageUrl": "https://images.unsplash.com/photo-1555066931-4365d14bab8c",
      "likeCount": 3,
      "createdAt": "2026-08-11T10:00:00",
      "updatedAt": "2026-08-11T10:00:00"
    }
    ```


## **3. Record DTO 기반 REST 컨트롤러 구현**

### **3.1 REST API DTO 설계와 Record 활용**

#### **1) REST API 계층에서 Record DTO를 채택하는 이유**

- 데이터 불변성 보장: 클라이언트 요청 파라미터나 서버 응답 데이터는 전송 과정에서 상태가 임의로 변조되지 않아야 하므로 불변(Immutable) 객체인 Record가 안전한 데이터 전송을 보장함.
- 기본 직렬화 및 역직렬화 지원: Spring Boot 4와 Jackson 라이브러리는 별도의 기본 생성자나 어노테이션 없이도 컴포넌트 메타데이터를 분석하여 JSON 직렬화와 역직렬화를 기본 지원함.
- 외부 라이브러리 의존성 배제: Lombok(`@Getter`, `@AllArgsConstructor` 등)에 대한 외부 라이브러리 의존 없이 순수 표준 자바 문법만으로 가독성 높은 DTO 코드를 유지할 수 있음.
- Record와 일반 클래스 선택 기준: 불변 데이터를 전달하는 조회 응답(`PostResponse`)이나 단순 수정 요청에는 Record가 가장 적합함. 반면 `PostCreateRequest`처럼 MyBatis의 `useGeneratedKeys` 및 `keyProperty`를 통해 데이터베이스 자동 생성 기본키(PK)를 사후에 수정자(`setId()`)로 주입받아야 하는 경우에는 가변 필드가 지원되는 일반 클래스(Lombok `@Getter`, `@Setter`)로 만들어야 함.

#### **2) DTO 명명 관례와 설계 전략**

- 전통적인 DTO 명칭: 데이터베이스와 서비스 내부 계층 간 데이터 교환 시에는 전통적으로 `~Dto`(예: `PostCreateDto`, `PostResponseDto`) 명칭을 주로 사용함.
- 모던 REST 웹 통신 규약: 외부 클라이언트와의 HTTP 통신을 전담하는 웹 계층에서는 데이터의 전송 방향과 역할을 명확히 구분하기 위해 `~Request`(요청 본문 및 검색 조건), `~Response`(응답 본문 데이터) 명칭을 주로 사용함.
- 계층별 분리 전략: 웹 계층 전용 Request/Response 객체와 서비스 계층용 DTO를 엄격히 분리하고 계층 경계에서 상호 변환하는 방식. 웹 스펙 및 검증 어노테이션의 변경이 핵심 비즈니스 계층으로 전파되는 것을 원천 차단하여 결합도를 낮출 수 있으나 계층 간 매핑 코드가 증가함.
- 단일 통일 전략: 별도의 서비스 DTO를 이중으로 만들지 않고 `PostCreateRequest`나 `PostResponse`를 서비스 계층까지 직접 전달하여 사용하는 방식. 중복 클래스 정의와 객체 변환 오버헤드를 없애 개발 생산성을 높이고 구조를 단순화할 수 있어 실무 프로젝트에서 자주 사용됨.

    ```java
    package net.likelion.bebc25.sns.dto;
    
    import jakarta.validation.constraints.NotBlank;
    import jakarta.validation.constraints.NotNull;
    import jakarta.validation.constraints.Size;
    import lombok.AllArgsConstructor;
    import lombok.Builder;
    import lombok.Getter;
    import lombok.NoArgsConstructor;
    import lombok.Setter;
    
    // 게시글 생성 요청 DTO (MyBatis keyProperty 자동 생성 PK 주입을 위해 일반 클래스 적용)
    @Getter
    @Setter
    @NoArgsConstructor
    @AllArgsConstructor
    @Builder
    public class PostCreateRequest {
        private Long id;
    
        @NotNull(message = "작성자 회원 번호는 필수 항목입니다.")
        private Long memberId;
    
        @NotBlank(message = "본문 내용은 필수 입력 항목입니다.")
        @Size(max = 1000, message = "본문은 1000자 이하여야 합니다.")
        private String content;
    
        private String imageUrl;
    
        // 클라이언트 요청 바디의 JSON을 역직렬화 할때 사용되는 생성자 추가
        public PostCreateRequest(Long memberId, String content, String imageUrl) {
            this.memberId = memberId;
            this.content = content;
            this.imageUrl = imageUrl;
        }
    }
    ```

### **4.3.3 서비스 계층 연계 및 반환 타입 변경**

#### **1) 기존 MyBatis(5단원) 서비스 계층과의 차이점**

- 기존 설계 (5단원): 게시글 등록(`createPost`) 시 데이터베이스에 레코드를 삽입한 후 생성된 식별자(PK)인 `Long` 타입의 ID만 반환하도록 구현함.
- REST API 요구사항: RESTful 웹 서비스에서는 자원 생성(`POST`) 요청 성공 시, 클라이언트가 등록된 자원의 상세 정보를 즉시 활용할 수 있도록 201 Created 상태 코드와 함께 생성된 자원의 전체 상태(`PostResponse`)를 응답 본문에 담아 반환하는 방식을 권장함.

#### **2) 정적 팩토리 메서드를 통한 응답 객체 조립**

- 불필요한 추가 조회 방지: 등록 직후 데이터베이스에서 레코드를 다시 조회(`SELECT`)하지 않고, 이미 메모리에 존재하는 요청 객체(`PostCreateRequest`)의 데이터와 MyBatis가 주입한 id(`dto.getId()`)를 활용함.
- 캡슐화 및 성능 최적화: `PostResponse.from(dto)` 정적 팩토리 메서드로 응답 객체를 즉시 조립하여 반환함으로써 불필요한 쿼리 실행 부하를 방지하고 서비스 로직의 가독성을 높임.
- 게시글 서비스 인터페이스 수정 (src/main/java/net/likelion/bebc25/sns/service/PostService.java)

    ```java
    // 기존 Long 반환에서 PostResponse 반환으로 변경
    PostResponse createPost(PostCreateRequest dto);
    ```

- 게시글 서비스 구현 클래스 수정 (src/main/java/net/likelion/bebc25/sns/service/PostServiceImpl.java)

    ```java
    @Override
    @Transactional(rollbackFor = Exception.class)
    public PostResponse createPost(PostCreateRequest dto) {
        postMapper.save(dto);
        return PostResponse.from(dto); // 정적 팩토리 메서드를 통해 응답 객체 즉시 생성
    }
    ```


### **4.3.4 PostRestController 구현**

- `ResponseEntity<T>`를 사용하여 HTTP 응답 상태 코드, 헤더, 본문 데이터를 정밀하게 제어함.
- HTTP 요청 데이터 바인딩 어노테이션 활용
    - `@PathVariable`: URI 경로에 포함된 고유 자원 식별자(`/{id}`)를 추출할 때 사용하며, 단건 자원의 조회, 수정, 삭제 처리에 주로 활용함.
    - `@RequestParam`: URL 쿼리 파라미터(`?key=value`)를 단일 변수에 1:1로 매핑할 때 사용하며, 전달받는 조건이 1~2개로 적을 때 적합함.
    - `@ModelAttribute`: 여러 개의 쿼리 파라미터나 폼 데이터(`key=value`)를 DTO/Record 객체로 한 번에 묶어서 매핑할 때 사용하며, 목록 검색 조건이나 페이징 처리에 주로 활용함.
    - `@RequestBody`: 클라이언트가 전송한 HTTP 요청 본문(Body)의 JSON 데이터를 자바 객체로 변환하여 주입받을 때 사용하며, 신규 자원 등록(`POST`)이나 수정(`PUT`, `PATCH`) 처리에 주로 사용함.
- 작성자 인가(Authorization) 사전 검증
    - 스프링 시큐리티 도입 전 단계이므로 `@RequestHeader("X-Member-Id")`를 통해 요청자의 식별자를 전달받아 처리함.
- 게시글 REST 컨트롤러 (src/main/java/net/likelion/bebc25/sns/controller/PostRestController.java)

    ```java
    package net.likelion.bebc25.sns.controller;
    
    import jakarta.validation.Valid;
    import net.likelion.bebc25.sns.dto.PostCreateRequest;
    import net.likelion.bebc25.sns.dto.PostResponse;
    import net.likelion.bebc25.sns.dto.PostSearchRequest;
    import net.likelion.bebc25.sns.dto.PostUpdateRequest;
    import net.likelion.bebc25.sns.service.PostService;
    import org.springframework.http.HttpStatus;
    import org.springframework.http.ResponseEntity;
    import org.springframework.web.bind.annotation.*;
    
    import java.net.URI;
    import java.util.List;
    
    @RestController
    @RequestMapping("/api/v1/posts")
    public class PostRestController {
    
        private final PostService postService;
    
        public PostRestController(PostService postService) {
            this.postService = postService;
        }
    
        // 1. 게시글 목록 조회 및 조건 검색 (200 OK)
        @GetMapping
        public ResponseEntity<List<PostResponse>> getPostList(
                @ModelAttribute PostSearchRequest searchRequest) {
            List<PostResponse> posts = postService.searchPosts(searchRequest);
            return ResponseEntity.ok(posts);
        }
    
        // 2. 게시글 단건 상세 조회 (200 OK)
        @GetMapping("/{id}")
        public ResponseEntity<PostResponse> getPostDetail(@PathVariable("id") Long id) {
            PostResponse post = postService.getPostById(id);
            return ResponseEntity.ok(post);
        }
    
        // 3. 신규 게시글 등록 (201 Created + Location 헤더)
        @PostMapping
        public ResponseEntity<PostResponse> createPost(
                @RequestHeader("X-Member-Id") Long memberId, // 사용자 인증 이전이므로 임시로 헤더에서 전달 받음
                @Valid @RequestBody PostCreateRequest request) {
            request.setMemberId(memberId); // memberId를 DTO에 주입
            PostResponse createdPost = postService.createPost(request);
            URI location = URI.create("/api/v1/posts/" + createdPost.id());
            return ResponseEntity.created(location).body(createdPost);
        }
    
        // 4. 게시글 수정 (200 OK 또는 403 Forbidden)
        @PutMapping("/{id}")
        public ResponseEntity<PostResponse> updatePost(
                @RequestHeader("X-Member-Id") Long memberId,
                @PathVariable("id") Long id,
                @Valid @RequestBody PostUpdateRequest request) {
            PostResponse post = postService.getPostById(id);
            if (!post.memberId().equals(memberId)) {
                return ResponseEntity.status(HttpStatus.FORBIDDEN).build();
            }
            postService.updatePost(id, request);
            PostResponse updatedPost = postService.getPostById(id);
            return ResponseEntity.ok(updatedPost);
        }
    
        // 5. 게시글 삭제 (204 No Content 또는 403 Forbidden)
        @DeleteMapping("/{id}")
        public ResponseEntity<Void> deletePost(
                @RequestHeader("X-Member-Id") Long memberId,
                @PathVariable("id") Long id) {
            PostResponse post = postService.getPostById(id);
            if (!post.memberId().equals(memberId)) {
                return ResponseEntity.status(HttpStatus.FORBIDDEN).build();
            }
            postService.deletePost(id);
            return ResponseEntity.noContent().build();
        }
    }
    ```
