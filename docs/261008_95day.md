# **하이버네이트 고급 매핑과 공통 속성 상속**

## **1. @Enumerated를 통한 역할(Role) 타입 안전성 확보**

- 도메인 모델에서 Enum으로 관리되는 대표적인 유형
    - 회원 권한 및 역할(Role): 서비스 인가와 접근 제어에 활용되는 권한 체계 (`USER`, `ADMIN`, `MANAGER`)
    - 비즈니스 진행 상태(Status): 도메인 프로세스의 생명주기 상태 (`ORDERED`, `PAYMENT_COMPLETED`, `SHIPPED`, `CANCELED`)
    - 결제 수단 및 거래 유형(Payment Type): 결제 방식이나 금융 거래 형태 (`CARD`, `BANK_TRANSFER`, `POINT`)
    - 소셜 로그인 제공자(OAuth Provider): 외부 인증 연동 공급자 구분 (`KAKAO`, `NAVER`, `GOOGLE`, `GITHUB`)
    - 이벤트 및 알림 유형(Notification Type): SNS 상호작용 및 알림 발생 이벤트 (`COMMENT`, `LIKE`, `FOLLOW`)
    - 콘텐츠 공개 범위(Visibility): 게시물 접근 제한 범위 (`PUBLIC`, `FRIENDS_ONLY`, `PRIVATE`)
- 회원의 권한을 기존의 단순 문자열(`String role = "USER"`)로 관리하면 오탈자로 인한 런타임 버그가 발생하기 쉬우므로 자바 Enum과 `@Enumerated(EnumType.STRING)`을 적용하여 컴파일 타임 타입 검증 구조로 전환.
- Role 열거형 (src/main/java/net/likelion/bebc25/jpasns/domain/Role.java)

    ```java
    package net.likelion.bebc25.jpasns.domain;
    
    public enum Role {
        USER, ADMIN
    }
    ```

- Enum 매핑 전략 비교
    - EnumType.ORDINAL: Enum에 정의된 순서(0, 1, 2...)를 숫자로 데이터베이스에 저장함. 기본 설정이지만 Enum 상수의 순서가 바뀌거나 중간에 새로운 상수가 추가되면 기존 저장된 데이터의 의미가 완전히 왜곡되는 치명적인 문제가 발생하므로 실무에서는 잘 사용하지 않음.
    - EnumType.STRING: Enum 상수의 이름("USER", "ADMIN")을 문자열 그대로 데이터베이스 컬럼에 저장함. 순서가 변경되거나 새로운 상수가 추가되어도 안전하게 데이터를 보존할 수 있으므로 이 옵션을 지정하는 걸 권장.
- Member 엔티티 적용 코드 (기존 String role 대체)

## **2. @Embedded 주소 값 타입(Address) 분리**

- 주소 세분화와 임베디드 타입 도입
    - 회원의 상세 정보(`MemberDetail`)에서 주소를 단순 단일 문자열(`String address = "서울특별시 강남구 테헤란로 123 4층 401호 (06234)"`)로 저장하면, SNS 프로필 화면에 노출 가능한 기본 도로명주소와 민감한 개인 사생활인 상세주소(동/호수)가 뒤섞여 개별 노출 제어 및 마스킹 처리가 어려움.
    - 동일 생활권 사용자 집계에 활용되는 우편번호(`zipcode`), 대외 공개용 도로명주소(`roadAddress`), 비공개 상세주소(`detailAddress`) 단위로 데이터를 명확히 분리하여 개인정보 보호와 데이터 정합성을 확보해야 함.
    - 이때 세분화된 주소 필드들을 엔티티에 단순 나열하지 않고, 서로 밀접하게 연관된 개념을 JPA의 임베디드 값 타입(`@Embeddable`, `@Embedded`)을 활용하여 `Address`라는 하나의 응집도 높은 객체로 묶어 관리함.
- 임베디드 타입(Embedded Type)의 정의 및 특징
    - JPA에서는 새로운 엔티티를 생성하지 않고도 관련 있는 여러 필드를 묶어 하나의 클래스로 정의할 수 있으며 이를 값 타입(Value Type)이라고 부름.
    - 정의하는 클래스에는 `@Embeddable`을 선언하고, 엔티티에서 해당 클래스를 필드로 사용할 때는 `@Embedded`를 선언함.
- 임베디드 주소 값 타입 (src/main/java/net/likelion/bebc25/jpasns/domain/Address.java)

    ```java
    package net.likelion.bebc25.jpasns.domain;
    
    import jakarta.persistence.Column;
    import jakarta.persistence.Embeddable;
    import lombok.AccessLevel;
    import lombok.Getter;
    import lombok.NoArgsConstructor;
    
    @Embeddable
    @Getter
    @NoArgsConstructor(access = AccessLevel.PROTECTED)
    public class Address {
    
        @Column(length = 10)
        private String zipcode;
    
        @Column(length = 100)
        private String roadAddress;
    
        @Column(length = 100)
        private String detailAddress;
    
        public Address(String zipcode, String roadAddress, String detailAddress) {
            this.zipcode = zipcode;
            this.roadAddress = roadAddress;
            this.detailAddress = detailAddress;
        }
    }
    ```

- MemberDetail 엔티티 수정 (기존 String address 필드를 임베디드 타입으로 교체)
    - 임베디드 타입은 테이블 생성 시 별도의 외래 키나 조인 테이블을 만들지 않고, 선언된 엔티티 테이블(`member_detail`)의 컬럼(`zipcode`, `road_address`, `detail_address`)으로 자연스럽게 펼쳐져 포함됨.

    ```java

    ...

        ...
    }

        ...
    }
    ```


## **3. @MappedSuperclass 공통 감사 엔티티(BaseTimeEntity) 상속**

- 감사 엔티티 (Auditing Entity): 데이터의 생성 및 수정 이력을 일관되게 기록하고 추적하기 위해 생성일시(`@CreatedDate`), 수정일시(`@LastModifiedDate`), 생성한사람(`@CreatedBy`), 수정한사람(`@LastModifiedBy`) 등의 공통 필드를 정의해 둔 상위 엔티티 클래스
- 테이블 컬럼 누락 방지와 상속을 통한 해결
    - 수작업으로 데이터베이스 테이블을 설계하고 엔티티를 작성하다 보면 특정 테이블(`post`)에는 `created_at`과 `updated_at`이 모두 정의되어 있으나, 다른 테이블(`member`)에는 `updated_at`이 누락되는 등 엔티티별 중복 선언과 컬럼 누락 실수가 빈번히 발생함.
    - JPA에서는 공통 필드를 추상 클래스로 분리하고 `@MappedSuperclass`를 선언한 뒤 모든 엔티티가 이를 상속받도록 구현함으로써, 특정 테이블에만 수정일시 컬럼이 빠지는 실수를 방지하고 모든 엔티티의 등록일시와 수정일시를 일관되게 관리할 수 있음.
- BaseTimeEntity 추상 클래스 (src/main/java/net/likelion/bebc25/jpasns/common/entity/BaseTimeEntity.java)

    ```java
    package net.likelion.bebc25.jpasns.common.entity;
    
    import jakarta.persistence.Column;
    import jakarta.persistence.EntityListeners;
    import jakarta.persistence.MappedSuperclass;
    import lombok.Getter;
    import org.springframework.data.annotation.CreatedDate;
    import org.springframework.data.annotation.LastModifiedDate;
    import org.springframework.data.jpa.domain.support.AuditingEntityListener;
    import java.time.LocalDateTime;
    
    @Getter
    @MappedSuperclass
    @EntityListeners(AuditingEntityListener.class)
    public abstract class BaseTimeEntity {
    
        @CreatedDate
        @Column(updatable = false)
        private LocalDateTime createdAt;
    
        @LastModifiedDate
        private LocalDateTime updatedAt;
    }
    ```

- 감사 어노테이션 핵심 구성 요소
    - @MappedSuperclass: 공통 매핑 정보를 담는 상위 추상 클래스임을 선언하며, 독립된 테이블을 생성하지 않고 자식 엔티티에 컬럼 정보만 상속함.
    - @EntityListeners(AuditingEntityListener.class): 엔티티의 영속화(Persist) 및 수정(Update) 이벤트를 감지하는 리스너를 연결함. 이 리스너가 등록되어 있어야 생성 및 수정 시점을 포착하여 날짜를 자동 주입할 수 있음.
    - @CreatedDate: 엔티티가 최초 저장될 때의 생성일시를 자동으로 기록함.
    - @LastModifiedDate: 엔티티가 최초 저장될 때 생성일시와 동일하게 기록되며, 이후 속성이 변경되어 저장될 때 수정일시를 자동으로 갱신함.
- JPA Auditing 활성화 설정
    - 별도 설정 클래스에 `@EnableJpaAuditing`을 선언하여 엔티티 등록 및 수정 시점에 날짜를 자동 주입하도록 활성화함.
    - JpaConfig 설정 클래스 (src/main/java/net/likelion/bebc25/jpasns/config/JpaConfig.java)

        ```java
        package net.likelion.bebc25.jpasns.config;
        ```

## **4. SNS 회원 엔티티 완성**

- 고급 매핑 기능(@Enumerated, @MappedSuperclass 상속)을 종합 적용하여 리팩토링한 회원 엔티티.
- SNS Member 엔티티 (src/main/java/net/likelion/bebc25/jpasns/domain/Member.java)

    ```java
    package net.likelion.bebc25.jpasns.domain;
    
    import jakarta.persistence.*;
    import lombok.AccessLevel;
    import lombok.Getter;
    import lombok.NoArgsConstructor;
    import net.likelion.bebc25.jpasns.common.entity.BaseTimeEntity;
    
    @Entity
    @Getter
    @NoArgsConstructor(access = AccessLevel.PROTECTED)
    public class Member extends BaseTimeEntity {
    
        @Id
        @GeneratedValue(strategy = GenerationType.IDENTITY)
        private Long id;
    
        @Column(nullable = false, unique = true, length = 100)
        private String email;
    
        @Column(nullable = false, length = 255)
        private String password;
    
        @Column(nullable = false, unique = true, length = 50)
        private String nickname;
    
        @Enumerated(EnumType.STRING)
        @Column(nullable = false, length = 20)
        private Role role;
    
        public Member(String email, String password, String nickname) {
            this(email, password, nickname, Role.USER);
        }
    
        public Member(String email, String password, String nickname, Role role) {
            this.email = email;
            this.password = password;
            this.nickname = nickname;
            this.role = role != null ? role : Role.USER;
        }
    
        public void changeNickname(String nickname) {
            this.nickname = nickname;
        }
    }
    ```

# **엔티티 연관관계 매핑과 도메인 모델 고도화**

## **1. 테이블 연관관계의 동작 원리와 특성**

### **1.1 외래 키(Foreign Key)를 통한 물리적 연결**

- 관계형 데이터베이스는 두 테이블 간의 관계를 맺을 때 외래 키(FK) 컬럼을 사용함.
- 부모 테이블의 기본 키(PK) 값을 자식 테이블의 특정 컬럼에 저장하여 두 레코드 간의 연관성을 형성함.
- 데이터베이스 엔진 수준에서 외래 키 제약조건(Foreign Key Constraint)을 선언하여 데이터 누락이나 고아 데이터를 방지하는 참조 무결성(Referential Integrity)을 강제함.

### **1.2 조인(JOIN) 연산을 통한 양방향 데이터 조회**

- 테이블 연관관계는 외래 키 하나만 존재하면 조인(JOIN) 쿼리를 통해 양방향 탐색이 가능함.
- `member` 테이블과 `post` 테이블이 `post.member_id` 외래 키로 연결되어 있을 때:
    - 회원 기준으로 게시글 목록 조회: `SELECT * FROM post p JOIN member m ON p.member_id = m.id WHERE m.id = 1`
    - 게시글 기준으로 작성자 정보 조회: `SELECT * FROM member m JOIN post p ON m.id = p.member_id WHERE p.id = 10`
    - 테이블 세상에서는 '방향(Direction)'이라는 개념이 물리적으로 존재하지 않으며, 외래 키 하나만으로 양방향 조회가 항상 성립함.

### **1.3 외래 키의 물리적 위치 규칙 (1:N 다중성 기준)**

- 1:N 관계에서 외래 키는 데이터 구조상 항상 다(N) 쪽 테이블에 배치됨.
- 한 명의 회원이 여러 개의 게시글을 작성할 때, 회원 테이블의 컬럼에는 여러 개의 게시글 번호를 배열 형태로 저장할 수 없으므로(제1정규형 원자값 원칙), 반드시 다(N) 측인 게시글 테이블에 `member_id` 외래 키를 두어야 함.

### **1.4 테이블 연관관계와 객체 연관관계의 근본적 패러다임 차이**

- 테이블 연관관계: 외래 키(FK) 하나로 양방향 조인 지원, 수량적 관계 중심.
- 객체 연관관계: 참조 필드(`post.getMember()`)가 선언된 방향으로만 단방향 이동 가능, 양방향 참조를 만들려면 양쪽 클래스 모두에 참조 필드를 선언하고 동기화 로직을 구성해야 함.

## **2. 단순 외래 키 숫자 보관 방식의 한계와 객체 참조 전환**

- `Post` 엔티티는 데이터베이스 테이블 컬럼 구조를 그대로 모방하여 `Long memberId`라는 단순 외래 키 숫자 값을 필드로 보관함.
- 객체가 다른 객체를 직접 참조하지 않고 단순 식별자 숫자만 저장하는 방식은 다음과 같은 객체지향 패러다임 불일치 문제를 야기함.

### **2.1 객체 그래프 탐색의 단절**

- 객체 세상에서는 게시글을 통해 작성자의 닉네임을 알고 싶다면 `post.getMember().getNickname()`처럼 점(.) 연산자로 자유롭게 객체를 타고 들어갈 수 있어야 함.
- 하지만 `Long memberId` 방식에서는 `post.getMemberId()`로 숫자 ID만 얻을 수 있을 뿐 작성자 객체를 직접 참조할 수 없어 객체 그래프 탐색이 완전히 단절됨.

### **2.2 비즈니스 로직 왜곡**

- 작성자 정보를 얻기 위해 서비스 계층에서 리포지토리나 EntityManager를 통해 `em.find(Member.class, post.getMemberId())`를 데이터베이스에 다시 쿼리해야 함.
- 결국 객체지향적인 협력 관계를 맺지 못하고, 객체가 데이터베이스 레코드 값을 단순 보관하는 수동적 데이터 전달체로 전락하게 됨.

### **2.3 패러다임 불일치 극복**

- JPA의 `@ManyToOne`과 `@JoinColumn`을 활용하면, 객체 세상에서는 `Member member`라는 온전한 객체 참조를 유지하면서도 데이터베이스 테이블에는 `member_id`라는 외래 키 컬럼이 자동으로 생성되고 바인딩되도록 연결할 수 있음.

## **3. JPA 연관관계 매핑의 3가지 핵심 기준**

### **3.1 다중성 (Multiplicity)**

- 엔티티 간의 수량적 대응 관계를 의미하며, JPA에서는 4가지 어노테이션을 제공함.
- `@ManyToOne` (다대일, N:1): 여러 엔티티가 하나의 대상을 참조함 (예: 여러 개의 게시글 `Post` 또는 댓글 `Comment`가 하나의 작성자 `Member`를 참조).
- `@OneToMany` (일대다, 1:N): 하나의 엔티티가 여러 엔티티 컬렉션을 가짐 (예: 하나의 게시글 `Post`가 여러 개의 댓글 `List<Comment>` 목록을 보유).
- `@OneToOne` (일대일, 1:1): 하나의 엔티티가 오직 하나의 대상 엔티티만 참조함 (예: 한 명의 회원 `Member`가 단 하나의 상세 정보 `MemberDetail`을 보유).
- `@ManyToMany` (다대다, N:M): 양쪽 엔티티가 서로 여러 대상을 참조함 (예: 게시글 `Post`와 태그 `Tag`의 관계이며, 실무에서는 `PostHashtag` 같은 연결 엔티티로 분리 설계 권장).

### **3.2 방향성 (Direction)**

- 단방향: 한쪽 엔티티만 상대방 엔티티의 참조 필드를 보유하여 한쪽 방향으로만 객체 탐색이 가능한 구조.
- 양방향: 양쪽 엔티티가 서로를 참조하여 양방향 객체 탐색이 가능한 구조 (실제로는 서로 다른 단방향 매핑 2개가 결합된 형태).

### **3.3 연관관계의 주인 (Owner)**

- 객체의 양방향 관계에서 데이터베이스 테이블의 외래 키(FK)를 실제로 관리(등록/수정)하는 주체를 지정하는 원칙.
- 데이터베이스 테이블 구조상 외래 키(FK) 컬럼을 보유한 테이블에 매핑되는 엔티티의 참조 필드를 연관관계의 주인으로 설정함.

## **4. 다대일 단방향 매핑과 핵심 속성**

### **4.1 @ManyToOne**

- 다대일(N:1) 관계임을 선언하는 핵심 어노테이션.

#### **1) `fetch` 속성**

- 연관 엔티티의 로딩 방식을 설정.
- `FetchType.EAGER`: 즉시 로딩 (기본값)
    - 엔티티를 조회할 때 연관된 엔티티를 데이터베이스에서 즉시 함께 조회하는 방식.
    - `em.find()` 단건 조회 시점에 연관 테이블과 조인(JOIN) 쿼리를 함께 실행하여 연관 객체까지 메모리에 온전히 채워 넣음.
    - JPQL 1이나 리포지토리 쿼리 실행 시 연관 엔티티를 조회하기 위한 추가 쿼리가 엔티티 건수만큼 반복 실행되는 N+1 문제 2 및 불필요한 조인 오버헤드가 발생하기 쉬움.
- `FetchType.LAZY`: 지연 로딩
    - 엔티티를 조회할 때 연관된 엔티티를 즉시 조회하지 않고 가짜 객체인 프록시(Proxy)로 채워 두는 방식.
    - 실제 연관 객체의 필드나 메서드를 참조하여 사용하는 최초 시점에 데이터베이스 쿼리를 실행하여 실제 데이터를 채움.
    - 불필요한 조인 연산을 방지하고 필요한 시점에만 쿼리를 발생시키므로 성능 최적화에 유리하며, 실무 연관관계 매핑의 기본 원칙으로 권장됨.
- 예시

    ```java
    public class Post {
        // 다대일 관계 (여러개의 Post가 동일한 Member를 가질 수 있음)
        @ManyToOne(fetch = FetchType.LAZY)
        private Member member; // 게시글의 작성자 정보
    
        ...
    }
    ```


#### **2) `optional` 속성**

- 연관된 엔티티가 null일 수 있는지 여부를 지정 (기본값: true).
- 기본값인 `optional = true` 상태에서는 연관 객체가 null일 수 있으므로 JPA가 외부 조인(`LEFT OUTER JOIN`)을 사용함.
- `optional = false`로 지정하면 반드시 연관 객체가 존재함(NOT NULL)이 보장되어, 데이터베이스에서 성능이 훨씬 우수한 내부 조인(`INNER JOIN`)으로 SQL 쿼리가 최적화됨.
- 반면, 익명으로 게시글 작성이 가능하다면 Post.member는 null이 될 수도 있으므로 `optional = true`로 지정해서 `LEFT OUTER JOIN`으로 조회하도록 해야 함.
- 예시

    ```java
    public class Post {
        // 작성자(Member)가 필수적으로 존재해야 함 (NOT NULL 관계 -> INNER JOIN 최적화)
        @ManyToOne(fetch = FetchType.LAZY, optional = false)
        private Member member;
    
        ...
    }
    ```


#### **3) `cascade` 속성**

- 엔티티의 영속 상태 변화를 연관된 엔티티에 전파할 범위를 지정 (기본값: 빈 배열 `{}`).
- 다대일 관계보다는 주로 부모가 자식을 관리하는 일대다(`@OneToMany`) 관계에서 활용되며, 상세한 동작 원리와 세부 옵션은 '3. 영속성 전이와 고아 객체 제거' 단원에서 다룸.

### **4.2 @JoinColumn**

- 테이블 상에 생성될 외래 키(FK) 컬럼을 명시.

#### **1) `name` 속성**

- 매핑할 외래 키 컬럼명을 직접 지정함 (기본값: `참조필드명_참조테이블기본키컬럼명`).
- 예시

    ```java
    public class Post {
        @ManyToOne(fetch = FetchType.LAZY, optional = false)
        @JoinColumn(name = "member_id") // post 테이블에 생성될 FK 컬럼명을 'member_id'로 지정 (생략 시 기본값도 'member_id')
        private Member member;
    
        ...
    }
    ```


#### **2) `referencedColumnName` 속성**

- 외래 키가 참조하는 대상 테이블의 컬럼명을 지정함 (기본값: 참조 대상 테이블의 기본 키 컬럼명).
- 대상 테이블의 PK 컬럼명이 아닌 특정 유니크(Unique) 컬럼을 FK로 참조하고자 할 때 명시함.
- 예시

    ```java
    public class Post {
        // Member 테이블의 PK(id) 대신 고유 식별값인 email 컬럼을 FK로 참조할 경우
        @ManyToOne(fetch = FetchType.LAZY, optional = false)
        @JoinColumn(name = "member_email", referencedColumnName = "email")
        private Member member;
    
        ...
    }
    ```


#### **3) `nullable` 속성**

- DDL 생성 시 외래 키 컬럼의 NOT NULL 제약 조건 부여 여부를 결정함 (기본값: true).
- 익명으로 게시글 작성이 가능하다면 member는 null값이 될 수 있기 때문에 `nullable = true`로 지정하고 반드시 로그인 한 상태에서만 게시글 작성이 가능하다면 `nullable = false`로 지정.
- 예시

    ```java
    public class Post {
        // DDL 생성 시 NOT NULL 제약 조건을 부여하여 DB 수준에서 NULL 저장을 차단
        @ManyToOne(fetch = FetchType.LAZY, optional = false)
        @JoinColumn(name = "member_id", nullable = false)
        private Member member;
    
        ...
    }
    ```


### **4.3 SNS 게시글 엔티티 단방향 객체 참조 매핑 구현**

- `Long memberId`를 제거하고 `@ManyToOne Member member` 객체 참조로 리팩토링한 Post 엔티티.
- Post 엔티티 (src/main/java/net/likelion/bebc25/jpasns/domain/Post.java)

    ```java
    package net.likelion.bebc25.jpasns.domain;
    
    import jakarta.persistence.*;
    import lombok.AccessLevel;
    import lombok.Getter;
    import lombok.NoArgsConstructor;
    import net.likelion.bebc25.jpasns.common.entity.BaseTimeEntity;
    
    @Entity
    @Table(name = "post")
    @Getter
    @NoArgsConstructor(access = AccessLevel.PROTECTED)
    public class Post extends BaseTimeEntity {
    
        @Id
        @GeneratedValue(strategy = GenerationType.IDENTITY)
        private Long id;
    
        @Column(nullable = false, columnDefinition = "TEXT")
        private String content;
    
        @Column(length = 255)
        private String imageUrl;
    
        @Column(nullable = false)
        private int likeCount;
    
        // Post 테이블의 member_id FK 컬럼으로 Member 테이블의 PK를 참조
        @ManyToOne(fetch = FetchType.LAZY, optional = false)
        @JoinColumn(name = "member_id", nullable = false)
        private Member member;
    
        public Post(String content, Member member) {
            this(content, null, member);
        }
    
        public Post(String content, String imageUrl, Member member) {
            this.content = content;
            this.imageUrl = imageUrl;
            this.member = member;
            this.likeCount = 0;
        }
    
        public void changeContent(String content) {
            this.content = content;
        }
    
        public void changeImageUrl(String imageUrl) {
            this.imageUrl = imageUrl;
        }
    
        public void update(String content, String imageUrl) {
            this.content = content;
            this.imageUrl = imageUrl;
        }
    
        public void increaseLikeCount() {
            this.likeCount++;
        }
    
        public void decreaseLikeCount() {
            if (this.likeCount > 0) {
                this.likeCount--;
            }
        }
    }
    ```


### **3.4 MemberPostTest 테스트 케이스 수정**

- Post 엔티티의 작성자 필드가 단순 숫자(`Long memberId`)에서 객체 참조(`Member member`)로 변경됨에 따라, 기존의 `new Post(content, savedMemberId)` 코드는 컴파일 에러가 발생함.
- 사전에 영속화된 Member 엔티티 객체를 조회하여 Post 생성자에 직접 전달하고, 조회 시 점(.) 연산자를 통한 객체 그래프 탐색(`findPost.getMember()`)이 정상 수행되는지 검증하도록 테스트 케이스를 수정함.
- MemberPostTest 수정 (src/test/java/net/likelion/bebc25/jpasns/domain/MemberPostTest.java)

    ```java
    void postSaveAndFind() {
        // 1. 변경: 영속 상태의 회원 조회 후 객체 참조를 전달하여 생성 (기존: new Post(content, savedMemberId))
        Member member = em.find(Member.class, savedMemberId);
        Post post = new Post("첫 번째 게시글 내용", member);
        em.persist(post);
    
        em.flush();
        em.clear();
    
        Post findPost = em.find(Post.class, post.getId());
    
        assertThat(findPost.getMember()).isNotNull();
        assertThat(findPost.getMember().getId()).isEqualTo(savedMemberId);
        assertThat(findPost.getMember().getNickname()).isEqualTo("테스터");
    }
    ```
