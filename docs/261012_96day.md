## **5. 양방향 연관관계와 연관관계의 주인**

### **5.1 양방향 연관관계가 필요한 경우**

- Post 엔티티가 댓글 목록(`List<Comment>`)을 보유해야 하는 경우
    - 게시글 상세 조회 시 게시글 본문과 함께 하위 댓글 목록을 한 번에 탐색하여 화면에 렌더링해야 할 경우.
    - 게시글 삭제 시 연관된 댓글도 함께 연쇄 삭제하는 부모-자식 생명주기 관리가 필요할 경우.
- Comment 엔티티가 게시글(`Post`)을 보유해야 하는 경우
    - 댓글 작성 시 원글 작성자에게 알림을 발송 하거나 원글 작성자에게 댓글 삭제 권한이 있다면 원글 작성자 정보 조회가 필요. ( `comment.getPost().getMember()`)
- post, comment 테이블 스키마

    ```sql
    -- 게시글 테이블
    CREATE TABLE post (
        id BIGINT AUTO_INCREMENT PRIMARY KEY,
        member_id BIGINT NOT NULL,
        content TEXT NOT NULL,
        image_url VARCHAR(255),
        like_count INT DEFAULT 0,
        created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
        updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
        FOREIGN KEY (member_id) REFERENCES member(id) ON DELETE CASCADE
    );
    
    -- 댓글 테이블
    CREATE TABLE comment (
        id BIGINT AUTO_INCREMENT PRIMARY KEY,
        post_id BIGINT NOT NULL, -- 외래키 컬럼 보유
        member_id BIGINT NOT NULL,
        content TEXT NOT NULL,
        created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
        FOREIGN KEY (post_id) REFERENCES post(id) ON DELETE CASCADE,
        FOREIGN KEY (member_id) REFERENCES member(id) ON DELETE CASCADE
    );
    ```

- Post, Comment 엔티티

    ```java
    public class Post {
      ...
      private List<Comment> comments;
    }
    
    public class Comment { // post_id 외래키를 보유하고 관리하는 주체
      ...
      private Post post; // 외래 키 관리 주체 (연관관계의 주인)
    }
    ```


### **5.2 연관관계의 주인과 mappedBy 원칙**

#### **1) 연관관계의 주인(Owner) 정의 및 판정 기준**

- 객체의 양방향 연관관계는 서로 다른 단방향 연관관계 2개로 구성되므로, 두 엔티티 중 하나를 지정하여 데이터베이스 외래 키(FK)를 관리하도록 설정해야 함.
- 외래 키 컬럼을 물리적으로 보유한 테이블에 매핑되는 엔티티(`Comment`)의 해당 참조 필드(`post`)가 연관관계의 주인이 됨.
- 연관관계의 주인만이 데이터베이스 외래 키를 등록 및 수정할 수 있으며, 주인이 아닌 쪽은 읽기(조회)만 가능함.
- 외래 키 관리의 실질적인 의미와 중요성
    - 외래 키 컬럼의 등록(INSERT) 결정
        - 연관관계의 주인 필드에 참조 객체가 할당되어야만 INSERT 쿼리 발생 시 외래 키 컬럼에 유효한 값이 반영됨.
        - 주인이 아닌 쪽(예: `post.getComments().add(comment)`)에만 값을 설정하고 주인 필드(`comment.setPost(post)`)를 설정하지 않으면, 데이터베이스 외래 키 컬럼에 null이 전달되어 무결성 제약조건 위반 예외가 발생함.
    - 대상 엔티티 레코드 수정과의 차이점
        - Comment의 post 필드를 변경하더라도 대상 `post` 테이블의 레코드 자체가 수정되는 것이 아니며, 오직 `comment` 테이블의 `post_id` 외래 키 컬럼 값만 UPDATE됨.
    - 실무 도메인 관점의 외래 키 변경(UPDATE)
        - 게시글-댓글과 같이 종속적인 관계에서는 외래 키 변경이 드물지만, 사원의 부서 이동, 상품의 카테고리 재지정 등 비즈니스 도메인에 따라 외래 키 수정(UPDATE) 역시 빈번하게 발생함.

#### **2) `@OneToMany`**

- 일대다 관계임을 선언하는 어노테이션.
- `mappedBy` 속성
    - 양방향 매핑에서 연관관계의 주인이 아닌 엔티티에 `@OneToMany(mappedBy = "...")` 형태로 선언하며, 주인의 매핑에 종속된 읽기 전용 상태임을 명시함.
    - 속성값으로는 데이터베이스 컬럼명이 아닌, 연관관계의 주인인 상대방 엔티티 클래스 내에 선언된 참조 필드명을 지정함.
    - 예시

        ```java
        // 1. 연관관계의 주인 (Comment 엔티티)
        public class Comment {
            @ManyToOne(fetch = FetchType.LAZY)
            @JoinColumn(name = "post_id", nullable = false)
            private Post post; // 외래 키(post_id) 직접 관리
        }
        
        // 2. 연관관계의 거울 (Post 엔티티)
        public class Post {
            // Comment 클래스의 post 필드명을 mappedBy 값으로 지정 (읽기 전용)
            @OneToMany(mappedBy = "post", cascade = CascadeType.ALL, orphanRemoval = true)
            private List<Comment> comments = new ArrayList<>();
        }
        ```

- `fetch`: 연관 엔티티 컬렉션의 로딩 방식을 설정함 (기본값: `FetchType.LAZY`).
- `cascade` (영속성 전이):
    - 특정 엔티티의 영속 상태 변화를 연관된 엔티티 컬렉션에 전파할 범위를 지정 (기본값: 빈 배열 `{}`).
    - 부모 엔티티를 저장하거나 삭제할 때 자식 엔티티도 함께 등록되거나 삭제되도록 생명주기를 동기화함. 부모와 자식 간의 생명주기가 거의 일치하고 자식 엔티티를 오직 해당 부모만 단독 소유할 때(Post와 Comment의 관계) 적용함. 자식이 다른 곳에서도 참조되고 있다면 사용을 삼가야 함.
    - 주요 CascadeType 옵션


        | **옵션 종류** | **설명 및 전파 동작** |
        | --- | --- |
        | CascadeType.PERSIST | 부모 저장 시 연관된 자식 엔티티도 함께 persist() 호출 |
        | CascadeType.MERGE | 부모 병합 시 연관된 자식 엔티티도 함께 merge() 호출 |
        | CascadeType.REMOVE | 부모 삭제 시 연관된 자식 엔티티도 함께 remove() 호출 |
        | CascadeType.ALL | 위의 모든 CascadeType 옵션을 한 번에 적용 |
- `orphanRemoval` (고아 객체 제거):
    - 부모 엔티티와 연관관계가 끊어진 자식 엔티티(고아 객체)를 자동으로 DELETE 쿼리 실행하여 삭제할지 여부를 지정 (기본값: false).
    - 부모 엔티티의 자식 컬렉션에서 특정 자식 객체를 제거(`post.getComments().remove(0)`)했을 때, 부모와의 연관관계가 끊어진 자식을 고아 객체로 감지하여 데이터베이스에서 자동으로 DELETE 쿼리를 실행함.
    - `CascadeType.REMOVE`와의 차이:
        - `CascadeType.REMOVE`: 부모 엔티티가 삭제될 때 자식을 함께 삭제함.
        - `orphanRemoval = true`: 부모 엔티티가 삭제될 때뿐만 아니라, 부모 컬렉션에서 참조만 끊겨도 자식 레코드를 DB에서 삭제 처리함.

### **5.3 댓글 엔티티와 양방향 편의 메서드 구현**

- `Long postId`, `Long memberId`를 객체 참조(`Post post`, `Member member`)로 리팩토링한 Comment 엔티티.
- Comment 엔티티 (src/main/java/net/likelion/bebc25/jpasns/domain/Comment.java)

    ```java
    package net.likelion.bebc25.jpasns.domain;
    
    import jakarta.persistence.*;
    import lombok.AccessLevel;
    import lombok.Getter;
    import lombok.NoArgsConstructor;
    import net.likelion.bebc25.jpasns.common.entity.BaseTimeEntity;
    
    @Entity
    @Table(name = "comment")
    @Getter
    @NoArgsConstructor(access = AccessLevel.PROTECTED)
    public class Comment extends BaseTimeEntity {
    
        @Id
        @GeneratedValue(strategy = GenerationType.IDENTITY)
        private Long id;
    
        @Column(columnDefinition = "TEXT", nullable = false)
        private String content;
    
        @ManyToOne(fetch = FetchType.LAZY, optional = false)
        @JoinColumn(name = "post_id", nullable = false)
        private Post post; // 외래 키 관리 주체 (연관관계의 주인)
    
        @ManyToOne(fetch = FetchType.LAZY, optional = false)
        @JoinColumn(name = "member_id", nullable = false)
        private Member member;
    
        public Comment(String content, Member member) {
            this.content = content;
            this.member = member;
        }
    
        // 댓글과 연관된 게시글을 지정 (Post에서 호출할 메서드)
        void assignPost(Post post) {
            this.post = post;
        }
    }
    ```

- Post 엔티티 양방향 컬렉션 확장 (src/main/java/net/likelion/bebc25/jpasns/domain/Post.java)

    ```java
    public class Post extends BaseTimeEntity {
        // ...
    
        @OneToMany(mappedBy = "post", cascade = CascadeType.ALL, orphanRemoval = true)
        private List<Comment> comments = new ArrayList<>();
    
        public void addComment(Comment comment) {
            this.comments.add(comment);
            comment.assignPost(this); // 양쪽 참조를 원자적으로 설정하는 편의 메서드
        }
    }
    ```


### **5.4 양방향 연관관계 매핑 테스트 케이스**

- 연관관계 편의 메서드(`addComment`)를 통한 상호 참조 설정과 영속성 전이(`CascadeType.ALL`)에 따른 양방향 객체 그래프 저장 및 탐색을 검증하는 테스트 코드.
- CommentTest.java (src/test/java/net/likelion/bebc25/jpasns/domain/CommentTest.java)

    ```java
    package net.likelion.bebc25.jpasns.domain;
    
    import jakarta.persistence.EntityManager;
    import org.junit.jupiter.api.BeforeEach;
    import org.junit.jupiter.api.DisplayName;
    import org.junit.jupiter.api.Test;
    import org.springframework.beans.factory.annotation.Autowired;
    import org.springframework.boot.test.context.SpringBootTest;
    import org.springframework.transaction.annotation.Transactional;
    
    import static org.assertj.core.api.Assertions.assertThat;
    
    @SpringBootTest
    @Transactional
    public class CommentTest {
    
        @Autowired
        private EntityManager em;
    
        private Long newMemberId;
        private Long newPostId;
        private Long newCommentId;
    
        @BeforeEach // 각 테스트 케이스 실행 전에 실행 코드
        void setUp(){
            // 1. 회원 등록
            Member member = new Member("haru@test.com", "1234", "하루");
            em.persist(member); // insert 쿼리문이 실행되어 회원이 등록됨
            this.newMemberId = member.getId(); // 새로 등록된 회원 id
    
            // 2. 게시글 등록
            Post post = new Post(member, "멍멍");
            em.persist(post); // insert 쿼리문이 실행되어 게시글이 등록됨
            this.newPostId = post.getId(); // 새로 등록된 게시글 id
    
            // 3. 댓글 등록
            Comment comment = new Comment("댓글1", member);
            comment.assignPost(post);
            em.persist(comment); // insert 쿼리문이 실행되어 댓글이 등록됨
            this.newCommentId = comment.getId(); // 새로 등록된 댓글 id
    
            em.clear(); // 캐시 삭제
        }
    
        @Test
        @DisplayName("댓글 등록")
    //    @Commit // 테스트 종료 후 롤백 시키지 않고 커밋함
        void create(){
            Post findPost = em.find(Post.class, newPostId);
            Member fineMember = em.find(Member.class, newMemberId);
    
            Comment comment = new Comment("댓글2", fineMember);
            comment.assignPost(findPost);
            em.persist(comment); // insert 쿼리문이 실행되어 댓글이 등록됨
    
            em.clear(); // 캐시를 비우기
    
            // 등록한 댓글을 조회
            Comment findComment = em.find(Comment.class, comment.getId()); // select 쿼리문이 실행되어 댓글이 조회됨
    
            // 조회한 댓글 정보를 이용해서 댓글 등록 검증
            assertThat(findComment).isNotNull();
            assertThat(findComment.getId()).isEqualTo(comment.getId());
            assertThat(findComment.getPost().getId()).isEqualTo(newPostId);
            assertThat(findComment.getMember().getNickname()).isEqualTo("하루"); // 댓글의 작성자가 "하루" 가 맞나?
            assertThat(findComment.getCreatedAt()).isNotNull();
        }
    
        @Test
        @DisplayName("댓글 조회")
        void read(){
            Comment findComment = em.find(Comment.class, newCommentId);
    
            // 영속성 컨텍스트의 1차 캐시값에서 즉시 반환되며 select 쿼리를 실행하지 않음
            Comment findComment2 = em.find(Comment.class, newCommentId);
    
            assertThat(findComment).isSameAs(findComment2); // 동일한 주소를 가지고 있는 객체인지 여부(==)
    
            assertThat(findComment).isNotNull();
            assertThat(findComment.getContent()).isEqualTo("댓글1");
            assertThat(findComment.getMember().getId()).isEqualTo(newMemberId);
            assertThat(findComment.getPost().getId()).isEqualTo(newPostId);
        }
    
        @Test
        @DisplayName("댓글 수정")
        void update(){
            Comment targetComment = em.find(Comment.class, newCommentId);
    
            // 엔티티의 속성이 수정되면 update 쿼리가 생성
            // 실행은 바로 되지 않고 버퍼에 저장되고 커밋 직전에 실행됨(쓰기 지연)
            targetComment.changeContent("수정된 댓글");
    
            em.flush(); // 버퍼의 데이터를 DB에 전송(실제 update 실행)
            em.clear();
    
            Comment updatedComment = em.find(Comment.class, newCommentId);
            assertThat(updatedComment.getContent()).isEqualTo("수정된 댓글");
        }
    
        @Test
        @DisplayName("댓글 삭제")
        void delete(){
            Comment targetComment = em.find(Comment.class, newCommentId);
            em.remove(targetComment); // delete 쿼리문 생성해서 쓰기 지연 SQL 버퍼에 저장
    
            em.flush();
            em.clear();
    
            Comment findComment = em.find(Comment.class, newCommentId);
            assertThat(findComment).isNull();
        }
    
        @Test
        @DisplayName("게시글-댓글 양방향 연관관계 매핑")
        void postCommentBiDirectionalMapping(){
            // 사용자, 게시글 조회
            Member member = em.find(Member.class, newMemberId);
            Post post = em.find(Post.class, newPostId);
    
            Comment comment2 = new Comment("댓글2", member);
            Comment comment3 = new Comment("댓글3", member);
    
            post.addComment(comment2);
            post.addComment(comment3);
    
            em.flush();
            em.clear();
    
            // 게시글 조회시 댓글 목록 확인(역방향 1 -> N)
            Post findPost = em.find(Post.class, newPostId);
            assertThat(findPost).isNotNull();
            assertThat(findPost.getComments()).hasSize(3);
            assertThat(findPost.getComments())
                    .extracting(Comment::getContent) // 컬랙션 내 엔티티들의 특정 필드를 추출
                    .containsExactly("댓글1", "댓글2", "댓글3"); // 추출된 값들이 내용과 순서가 일치하는지 확인
            em.flush();
            em.clear();
    
            // 댓글 조회시 게시글 확인(정방향 N -> 1)
            Comment findComment = em.find(Comment.class, comment2.getId());
            assertThat(findComment).isNotNull();
            assertThat(findComment.getPost().getId()).isEqualTo(post.getId());
            assertThat(findComment.getPost().getMember().getNickname()).isEqualTo("하루");
            assertThat(findComment.getPost().getContent()).isEqualTo("멍멍");
            assertThat(findComment.getMember().getEmail()).isEqualTo("haru@test.com");
        }
    
        @Test
        @DisplayName("Post를 통한 Comment 삭제")
        void postCommentBiDirectionalMappingDelete(){
            Post findPost = em.find(Post.class, newPostId);
            assertThat(findPost).isNotNull();
            assertThat(findPost.getComments()).hasSize(1);
    
            // 댓글 삭제
            findPost.getComments().removeFirst();
            em.flush();
            em.clear();
    
            Post findPost2 = em.find(Post.class, findPost.getId());
            assertThat(findPost2).isNotNull();
            assertThat(findPost2.getComments()).hasSize(0);
        }
    }
    ```

- 주요 검증 포인트
    - 연관관계 편의 메서드 원자성: `post.addComment(comment)`를 호출하여 게시글의 댓글 컬렉션 추가와 댓글의 게시글 외래 키 참조 설정을 한 번에 안전하게 수행함.
    - 영속성 전이 동작: 부모 엔티티(`Post`)에 포함된 자식 엔티티(`Comment`)들이 별도의 `em.persist()` 호출 없이도 데이터베이스에 함께 INSERT 등록됨.
    - 고아 객체 자동 제거: 부모 엔티티의 컬렉션에서 자식 객체를 제거(`removeFirst()`)하면 연관관계가 끊어진 자식 엔티티를 고아 객체로 판단하여 데이터베이스 DELETE 쿼리를 자동 실행함.
    - 양방향 객체 그래프 탐색: 게시글에서 댓글 목록(`findPost.getComments()`)을 조회할 수 있을 뿐 아니라, 댓글에서도 해당 게시글(`findComment.getPost()`)을 자유롭게 탐색할 수 있음을 검증함.

## **6. 일대일 연관관계와 엔티티 수직 분할**

### **6.1 일대일(@OneToOne) 매핑 구조와 외래 키 위치 전략**

회원(Member)과 회원의 상세 정보(MemberDetail)처럼 1:1로 대응되는 관계를 매핑할 때 `@OneToOne`을 사용함. 일대일 관계에서는 어느 테이블에 외래 키를 둘 것인지 선택해야 함.

- 주 테이블(Member)에 외래 키를 두는 방식
    - 주 객체가 대상 객체의 참조를 가지듯이 주 테이블에 외래 키를 둠.
    - 회원 테이블만 조회해도 상세 정보 존재 여부를 즉시 파악할 수 있어 객체지향 개발자들이 선호함.
- 대상 테이블(MemberDetail)에 외래 키를 두는 방식
    - 전통적인 데이터베이스 설계자들이 선호하며, 향후 1:1 관계가 1:N으로 확장될 때 테이블 구조를 그대로 유지할 수 있음.

### **6.2 일대일 양방향 매핑 시 지연 로딩 한계**

- 대상 테이블에 외래 키를 둔 상태에서 주 테이블(Member)을 조회할 경우, Member 테이블 자체에는 외래 키 컬럼이 없으므로 MemberDetail이 존재하는지 확인하려면 어차피 MemberDetail 테이블을 쿼리해 보아야 함.
- 따라서 프록시 객체를 만들어 넣을지 `null`을 넣을지 판별할 수 없어 `FetchType.LAZY`로 설정하더라도 즉시 로딩(EAGER)으로 강제 전환되는 한계가 발생함. 실무에서는 주 테이블에 외래 키를 배치하는 단방향 설계를 주로 권장함.

### **6.3 @OneToOne**

- 일대일(1:1) 관계임을 선언하는 어노테이션.
- 속성 지원 특성
    - 앞서 살펴본 `@ManyToOne`과 `@OneToMany`의 핵심 속성들(`fetch`, `optional`, `mappedBy`, `cascade`, `orphanRemoval`)을 동일하게 지원함.
    - 단일 객체를 참조하므로 `optional`을 지원하며, 양방향 매핑 시 연관관계의 주인이 아닌 쪽에 `mappedBy`를 지정하고, 부모-자식 간 생명주기 통제를 위해 `orphanRemoval`을 지원함.

### **6.4 @MapsId**

- 식별 관계(Identifying Relationship)에서 자식 엔티티의 기본 키(PK)가 부모 엔티티의 기본 키(PK)를 그대로 물려받아 자신의 PK이자 외래 키(FK)로 동시에 사용할 때 선언하는 어노테이션.

#### **1) value 속성**

- 매핑할 부모 엔티티의 기본 키와 대응되는 식별자 속성명을 지정 (기본값: 빈 문자열 `""`).
- 단일 기본 키 매핑인 경우 속성값을 생략(`@MapsId`)하면 자식 엔티티의 `@Id` 필드와 자동으로 매핑됨.
- 복합 키(`@EmbeddedId`)를 사용하는 식별 관계에서는 복합 키 클래스 내부의 특정 식별자 필드명을 명시할 때 사용함.

#### **2) 식별 관계 동작 원리와 테이블 최적화**

- 자식 엔티티의 `@Id` 필드에 `@GeneratedValue`를 부여하지 않고, 연관된 부모 엔티티의 PK 값을 자식 엔티티의 식별자(PK)로 공유하여 매핑함.
- 1:1 수직 분할 구조에서 별도의 인조 키(ID) 컬럼과 추가 인덱스를 생성하지 않고 부모의 PK 하나만으로 관계를 완성하므로, 저장 공간을 절약하고 조인 성능을 최적화할 수 있음.

### **6.5 SNS 회원 상세 엔티티 구현 (@MapsId 1:1 식별 관계)**

- 회원의 상세 소개, 주소, 마케팅 수신동의를 보관하는 `member_detail` 테이블(`member_id`, `introduction`, `address`, `marketing_agreed`)은 `member` 테이블의 PK(`id`)를 그대로 자신의 PK이자 외래 키(FK)로 사용하는 1:1 수직 분할 구조.
- MemberDetail 엔티티 (src/main/java/net/likelion/bebc25/jpasns/domain/MemberDetail.java)

## **7. 복합 행위 엔티티와 N:M 해시태그 구조 개편**

### **7.1 초기 단일 해시태그 테이블 엔티티 모델링과 한계**

- 게시글 ID와 태그명을 단순히 한 테이블에 묶어 저장하는 `post_hashtag` 테이블(`id`, `post_id`, `tag_name`) 구조를 엔티티로 매핑하면 다음과 같은 형태가 됨.
- 해시태그 구조 개편 개편 전: 단일 해시태그 테이블 구조 (문자열 중복 보관)

    ```mermaid
    erDiagram
      POST ||--o{ POST_HASHTAG : "1 : N"
      POST {
          bigint id PK
          text content
      }
      POST_HASHTAG {
          bigint id PK
          bigint post_id FK
          varchar tag_name "태그 문자열 직접 저장 (중복 발생)"
      }
    ```

- 해시태그 구조 개편 개편 후: 독립 Tag 엔티티 및 연결 엔티티를 통한 N:M 정규화 구조

    ```mermaid
    erDiagram
        POST ||--o{ POST_HASHTAG : "1 : N"
        TAG ||--o{ POST_HASHTAG : "1 : N"
        POST {
            bigint id PK
            text content
        }
        POST_HASHTAG {
            bigint id PK
            bigint post_id FK
            bigint tag_id FK
        }
        TAG {
            bigint id PK
            varchar name UK "고유 태그명 관리"
        }
    ```

- 초기 PostHashtag 엔티티 (src/main/java/net/likelion/bebc25/jpasns/domain/PostHashtag.java)

    ```java
    package net.likelion.bebc25.jpasns.domain;
    
    import jakarta.persistence.*;
    import lombok.AccessLevel;
    import lombok.Getter;
    import lombok.NoArgsConstructor;
    
    @Entity
    @Getter
    @NoArgsConstructor(access = AccessLevel.PROTECTED)
    public class PostHashtag {
    
        @Id
        @GeneratedValue(strategy = GenerationType.IDENTITY)
        private Long id;
    
        @ManyToOne(fetch = FetchType.LAZY)
        @JoinColumn(name = "post_id", nullable = false)
        private Post post;
    
        @Column(name = "tag_name", nullable = false, length = 50)
        private String tagName;
    
        public PostHashtag(Post post, String tagName) {
            this.post = post;
            this.tagName = tagName;
        }
    }
    ```

- 기존 단일 테이블 방식의 한계와 정규화 변경 사유
    - 데이터 중복과 저장 공간 낭비: 수많은 게시글에 동일한 태그('#spring', '#jpa')가 달릴 때마다 문자열 'spring', 'jpa'가 매 행마다 중복 저장되어 저장 공간 낭비와 인덱스 비대화를 초래함.
    - 태그 검색 및 자동완성 시 DISTINCT 부하: 검색창이나 글 작성창에서 태그 자동완성을 지원할 때, 단일 테이블에서는 대용량 테이블 전체를 대상으로 `SELECT DISTINCT tag_name`을 실행해야 하므로 심각한 데이터베이스 CPU 부하와 인덱스 스캔 병목이 발생함.
    - 인기 태그 순위 및 통계 집계 비효율: 메인 화면의 실시간 인기 태그 TOP 10이나 태그별 게시글 수를 집계하기 위해 매번 수천만 행을 상대로 `GROUP BY tag_name`을 수행해야 하므로 쿼리 성능이 저하됨.
    - 태그 자체의 도메인 속성(메타데이터) 확장 한계: 태그 팔로우 기능, 유해 태그/금지어 차단 관리(`is_blocked`), 태그 상세 소개글 등 태그 고유의 메타데이터가 추가될 때 단일 테이블 구조에서는 모든 게시글 행마다 중복 컬럼을 추가해야 하므로 도메인 확장이 불가능함.
    - N:M 관계의 정규화 필요성: 하나의 게시글에 여러 태그가 달리고, 하나의 태그 역시 여러 게시글에 소속될 수 있는 전형적인 다대다(N:M) 관계이므로, 독립된 `Tag` 엔티티와 이를 이어주는 연결 엔티티로 정규화하는 것이 객체지향 및 데이터베이스 설계 표준에 부합함.

### **7.2 @ManyToMany 어노테이션의 한계와 정규화 설계 방안**

- JPA가 제공하는 `@ManyToMany`는 두 엔티티 사이에 연결 조인 테이블을 자동으로 만들어 주어 편리해 보이지만 실무에서는 거의 사용하지 않음.
- 실무 사용 불가 사유
    - 자동 생성되는 중간 테이블에 비즈니스상 필수적인 추가 컬럼(태그 등록일시, 등록자, 정렬 순서 등)을 추가할 수 없음.
    - 개발자가 인지하지 못하는 숨겨진 조인 쿼리가 발생하여 복잡한 실무 환경에서 SQL 쿼리 튜닝과 성능 최적화가 어려움.
- 해결 방안
    - 다대다 관계를 1:N, N:1 두 개의 다대일 관계로 풀어내고, 중간 테이블을 독립된 연결 엔티티(`PostHashtag`)로 승격하여 직접 매핑함.

### **7.3 독립 도메인 Tag 엔티티 정의**

- 태그명 중복을 방지하고 고유한 태그 데이터를 관리하기 위해 독립된 `Tag` 엔티티를 정의.
- Tag 엔티티 (src/main/java/net/likelion/bebc25/jpasns/domain/Tag.java)

    ```java
    package net.likelion.bebc25.jpasns.domain;
    ```

### **7.4 PostHashtag 연결 엔티티 수정 및 다대다 정규화 완성**

- 단순 문자열 컬럼(`tagName`)으로 관리하던 `PostHashtag` 엔티티를, 정규화된 `Tag` 엔티티와 `Post` 엔티티를 다대일 관계로 연결하는 복합 매핑 엔티티로 수정.
- 동일 게시글에 같은 태그가 중복 연결되지 않도록 `post_id`와 `tag_id`에 복합 유니크 제약 조건 설정.
- PostHashtag 엔티티 (src/main/java/net/likelion/bebc25/jpasns/domain/PostHashtag.java)

    ```java
    package net.likelion.bebc25.jpasns.domain;
    
    import jakarta.persistence.*;
    import lombok.AccessLevel;
    import lombok.Getter;
    import lombok.NoArgsConstructor;
    import net.likelion.bebc25.jpasns.common.entity.BaseTimeEntity;
    
    @Entity
    @Table(name = "post_hashtag", uniqueConstraints = {
        @UniqueConstraint(name = "uk_post_hashtag", columnNames = {"post_id", "tag_id"})
    })
    @Getter
    @NoArgsConstructor(access = AccessLevel.PROTECTED)
    public class PostHashtag extends BaseTimeEntity {
    
        @Id
        @GeneratedValue(strategy = GenerationType.IDENTITY)
        private Long id;
    
        @ManyToOne(fetch = FetchType.LAZY, optional = false)
        @JoinColumn(name = "post_id", nullable = false)
        private Post post;
    
        @ManyToOne(fetch = FetchType.LAZY, optional = false)
        @JoinColumn(name = "tag_id", nullable = false)
        private Tag tag;
    
        public PostHashtag(Post post, Tag tag) {
            this.post = post;
            this.tag = tag;
        }
    }
    ```


### **7.5 해시태그 N:M 정규화 매핑 테스트 케이스**

- 독립 `Tag` 엔티티와 다대다 연결 엔티티(`PostHashtag`)의 등록 및 단방향 객체 그래프 탐색, 그리고 복합 유니크 제약조건을 검증하는 테스트 코드.
- 테스트 코드 (src/test/java/net/likelion/bebc25/jpasns/domain/MemberPostTest.java)

    ```java
    @Test
    @DisplayName("게시글-태그 연결 엔티티 등록 및 다대일 객체 탐색 검증")
    void postHashtagSaveAndGraphTraversal() {
        // 1. 작성자 회원 및 게시글 생성
        Member member = em.find(Member.class, savedMemberId);
        Post post = new Post("해시태그 테스트 게시글", member);
        em.persist(post);
    
        // 2. 독립 Tag 엔티티 생성 및 영속화
        Tag springTag = new Tag("SpringBoot");
        Tag jpaTag = new Tag("JPA");
        em.persist(springTag);
        em.persist(jpaTag);
    
        // 3. 다대다 연결 엔티티(PostHashtag) 생성 및 영속화
        PostHashtag postHashtag1 = new PostHashtag(post, springTag);
        PostHashtag postHashtag2 = new PostHashtag(post, jpaTag);
        em.persist(postHashtag1);
        em.persist(postHashtag2);
    
        em.flush();
        em.clear();
    
        // 4. 연결 엔티티 조회를 통한 다대일 단방향 객체 탐색 검증
        PostHashtag findHashtag = em.find(PostHashtag.class, postHashtag1.getId());
        assertThat(findHashtag).isNotNull();
        assertThat(findHashtag.getPost().getId()).isEqualTo(post.getId());
        assertThat(findHashtag.getPost().getContent()).isEqualTo("해시태그 테스트 게시글");
        assertThat(findHashtag.getTag().getId()).isEqualTo(springTag.getId());
        assertThat(findHashtag.getTag().getName()).isEqualTo("SpringBoot");
    }
    
    @Test
    @DisplayName("동일 게시글에 동일 태그 중복 연결 시 복합 유니크 제약조건 위반 검증")
    void duplicatePostHashtagThrowsException() {
        // 1. 게시글 및 태그 생성
        Member member = em.find(Member.class, savedMemberId);
        Post post = new Post("중복 태그 테스트 게시글", member);
        em.persist(post);
    
        Tag tag = new Tag("Java");
        em.persist(tag);
    
        // 2. 첫 번째 해시태그 연결 등록
        PostHashtag firstHashtag = new PostHashtag(post, tag);
        em.persist(firstHashtag);
        em.flush();
    
        // 3. 동일한 게시글에 동일한 태그로 두 번째 연결 등록 시도 시 예외 발생 검증
        PostHashtag duplicateHashtag = new PostHashtag(post, tag);
    
        // IDENTITY 전략은 PK 채번을 위해 em.persist() 호출 즉시 INSERT 쿼리가 실행되므로 persist 시점에 복합 유니크 위반 예외 발생
        assertThatThrownBy(() -> {
            em.persist(duplicateHashtag);
            em.flush();
        }).isInstanceOf(Exception.class);
    }
    ```

- 주요 검증 포인트
    - N:M 정규화 객체 그래프 탐색: 연결 엔티티(`PostHashtag`)를 통해 부모 게시글(`Post`)과 고유 태그(`Tag`)로의 다대일 단방향 참조 탐색이 각각 정확하게 수행됨을 확인.
    - 복합 유니크 제약조건 무결성 보장: 동일 게시글에 같은 태그가 중복 연결되는 것을 DB 복합 유니크 제약조건(`uk_post_hashtag`)을 통해 원천 차단함을 검증함.
    - IDENTITY 전략의 예외 발생 시점: `GenerationType.IDENTITY` 전략은 기본 키 채번을 위해 `em.persist()` 호출 즉시 쓰기 지연 없이 INSERT 쿼리가 실행되므로, `em.flush()`가 아닌 `em.persist()` 시점에 즉시 유니크 제약조건 위반 예외가 발생함.

### **7.6 회원-게시글 다대다 행위 매핑 엔티티 구현 (PostLike, Bookmark)**

- 해시태그(`PostHashtag`)가 게시글(Post)과 태그(Tag) 사이의 다대다 연결이라면, 좋아요(`post_like`)와 북마크(`bookmark`)는 회원(Member)과 게시글(Post) 사이에서 발생하는 다대다 상호작용을 매핑하는 핵심 테이블.
- 두 엔티티는 특정 회원(`member_id`)과 대상 게시글(`post_id`)을 매핑하는 연관관계 구조가 완전히 동일함.
- JPA에서는 `@MappedSuperclass`를 활용하여 동일한 외래 키 매핑 필드와 등록일시/수정일시 감사 속성을 공통 부모 클래스(`BasePostReaction`)로 추상화하고, 자식 엔티티는 테이블 수준의 복합 유니크 제약 조건(`uk_member_post_like`, `uk_member_post_bookmark`)만 부여하여 중복 없이 상속 구현이 가능.
- 상호작용 공통 매핑 클래스 (src/main/java/net/likelion/bebc25/jpasns/domain/BasePostReaction.java)

    ```java
    package net.likelion.bebc25.jpasns.domain;
    
    import jakarta.persistence.*;
    import lombok.AccessLevel;
    import lombok.Getter;
    import lombok.NoArgsConstructor;
    import net.likelion.bebc25.jpasns.common.entity.BaseTimeEntity;
    
    @MappedSuperclass
    @Getter
    @NoArgsConstructor(access = AccessLevel.PROTECTED)
    public abstract class BasePostReaction extends BaseTimeEntity {
    
        @Id
        @GeneratedValue(strategy = GenerationType.IDENTITY)
        private Long id;
    
        @ManyToOne(fetch = FetchType.LAZY, optional = false)
        @JoinColumn(name = "post_id", nullable = false)
        private Post post;
    
        @ManyToOne(fetch = FetchType.LAZY, optional = false)
        @JoinColumn(name = "member_id", nullable = false)
        private Member member;
    
        public BasePostReaction(Post post, Member member) {
            this.member = member;
            this.post = post;
        }
    }
    ```

- PostLike 엔티티 (src/main/java/net/likelion/bebc25/jpasns/domain/PostLike.java)
